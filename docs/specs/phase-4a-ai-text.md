## 1. 目標與成功樣貌

記一筆帳要選帳本、型別、金額、日期、分類、帳戶，手機上尤其麻煩。本步讓使用者打一句話，系統拆成交易草稿，使用者看過、改過、確認後才寫入。

例子：我在「日常」帳本的交易頁。我的帳戶有「現金」「信用卡」「儲蓄」；「日常」的支出分類有「早餐」「午餐」「交通」；另有一本私人帳本「旅行基金」，只有支出分類「住宿」與收入分類「薪資」。今天是 2026-10-21。

1. 首頁與交易頁的頂端橫條最右邊有一個星芒圖示。我在交易頁點它，輸入欄向左展開。我打「早餐 60 現金、午餐 120 刷卡」，按送出，輸入欄清空並收起（2026-10-26 修訂，見 W246～W248；在首頁操作的樣子見 W252）。
2. 下方出現 2 筆草稿：「支出 · 早餐 · $60 · 10/21 · 早餐 · 現金」「支出 · 午餐 · $120 · 10/21 · 午餐 · 信用卡」。每筆有 ✓ 與 ×，下面一顆「全部確認」。
3. 我按第 1 筆的 ✓ → 它寫入「日常」，從草稿清單消失，明細多一筆早餐。
4. 我點第 2 筆 → 右側欄打開現有的記帳表單，欄位都帶好。我把金額改成 $125，按「新增」→ 寫入，草稿消失。
5. 我打「昨天計程車 250」→ 1 筆草稿：日期 10/20、分類「交通」、帳戶是記帳表單現在的預設（最近一次用的）。
6. 我打「從儲蓄轉 5000 到現金」→ 1 筆轉帳草稿：儲蓄 → 現金、$5,000、沒有分類。
7. 我打「旅行基金 機票 8000 刷卡」→ 草稿的帳本是「旅行基金」。「旅行基金」沒有對得到的分類 → 分類空著、標出要補。這筆不能按 ✓，「全部確認」也會跳過它，要先點開補分類。
8. 我打「今天天氣很好」→ 顯示「看不懂」，沒有草稿。
9. 我按 × → 草稿消失，什麼都沒寫入。

### 範圍外

- **4b**：共享帳本的付款人與分帳（「小明付晚餐 900，三人平分」）、借還（「借小華 500」）。4a 的共享帳本草稿付款人一律是我、不分帳。
- **4c**：查詢（「這個月吃飯花多少」）。
- **修改或刪除既有交易**：AI 找錯交易就會改錯資料，而且不容易發現。不排進任何一期，要的話另案討論。
- **新增分類、帳戶、帳本、對象**：AI 只能挑現有的。分類已由 [4a 補充](phase-4a-ai-new-category.md) 改成「沒有合適的才提議新增」，帳戶、帳本、對象不變。
- 語音輸入、本地模型（階段五）；行動 App。
- 費用上限與每日額度（開發者 2026-10-21：功能正常後再設）。已由 [4a 補充：每日額度](phase-4a-ai-quota.md) 處理。

## 4. API

### 4.1 `POST /ai/parse-transaction`（新）

`AiModule`，`@ApiTags('ai')`。需要登入。

> 2026-10-24：回應的草稿多一欄 `newCategoryName`，新增交易的請求多一個選填欄位 `newCategoryName`。見 [4a 補充](phase-4a-ai-new-category.md) §4。

Request：

```ts
interface ParseTransactionRequest {
  /** 1～200 字，前後空白會先去掉。 */
  text: string;
  /** 目前所在的帳本。必須是我能寫入的帳本，否則 404（不存在或沒權限）／403（檢視者）／409（封存）。 */
  ledgerId: string;
  /** 前端的今天，`YYYY-MM-DD`（決策 241）。 */
  today: string;
}
```

Response 200：

```ts
interface TransactionDraft {
  ledgerId: string;
  type: ManualTransactionType;
  /** 單位：分。對不到或不合法是 null。 */
  amount: Cents | null;
  /** `YYYY-MM-DD`。 */
  date: string | null;
  title: string | null;
  /** 支出／收入用；轉帳恆為 null。 */
  categoryId: string | null;
  /** 支出／收入的帳戶，或轉帳的轉出帳戶。 */
  accountId: string | null;
  /** 只有轉帳用。 */
  toAccountId: string | null;
}

interface ParseTransactionResponse {
  /** 0～10 筆。0 筆＝看不懂。 */
  drafts: TransactionDraft[];
}
```

錯誤：400（`text` 空白或超過 200 字、`today` 格式錯）、401、403／404／409（帳本權限，同新增交易）、429（限流）、503（AI 沒設定，或 provider 回錯誤、逾時）。503 的訊息不帶 provider 的原始錯誤。

「草稿完整」的判斷（W210 的 ✓ 能不能按）：支出／收入要有金額、日期、分類、帳戶；轉帳要有金額、日期、兩個不同的帳戶。這條規則放 `packages/shared` 的純函式，前後端共用（同 `專案決策脈絡.md`「只有一份實作」）。

上面的型別與「草稿完整」的函式放 `packages/shared/src/types/ai.ts`。

## 5. 成功條件

- **SC-P2**（確認＝現有 API）：按 ✓ 與「全部確認」只呼叫 `POST /ledgers/{ledgerId}/transactions`；寫入的交易與手動記的一樣（同樣出現在列表、同樣影響餘額）。
- **SC-P3**（日期）：`today=2026-10-21`、「昨天」→ `2026-10-20`；沒提日期 → `2026-10-21`。
- **SC-P4**（帳戶預設）：沒提帳戶 → 草稿帳戶＝`record-defaults` 的帳戶。
- **SC-P5**（轉帳）：§1 第 6 步 → `type: TRANSFER`、`accountId`＝儲蓄、`toAccountId`＝現金、`categoryId: null`。
- **SC-P6**（指定帳本）：§1 第 7 步（旅行基金只有「住宿」「薪資」）→ `ledgerId`＝旅行基金、`categoryId: null`。提到我只能檢視的帳本 → 用目前帳本。第 7 步 2026-10-24 起改為 `newCategoryName`＝交通，`categoryId: null`（假 provider 的劇本；見 [4a 補充](phase-4a-ai-new-category.md) §5）。

- **SC-P9**（權限與限流）：別人的帳本 → 404；檢視者 → 403；封存 → 409；同一個使用者第 11 次（1 分鐘內）→ 429；沒設定 AI → 503。
- **SC-P10**（真的模型）：接上 GLM 後，§1 第 1、5、6、7、8 步的 5 句各跑 3 次，共 15 次。每次都在 25 秒內回 200。第 1、5、6、7 步每次的型別、金額、日期、分類、帳戶都對；第 8 步每次都是 0 筆。結果填進 plan §1.7 的表，失敗也照記。加入新分類提議之後的真模型驗收見 [4a 補充](phase-4a-ai-new-category.md) SC-P17。

## 7. 界線
