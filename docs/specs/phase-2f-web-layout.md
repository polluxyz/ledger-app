## 1. 目標與成功樣貌

把 `apps/web` 從「一根 640px 窄欄」改成**桌機取向的 dashboard 版面**，並補齊 `global.css`
的設計 token。

現況的根因只有一行：`apps/web/src/App.module.css:3` 的 `max-width: 40rem`。
全站每一頁都擠在這根欄裡置中，內容只能一路往下疊——那是手機 App 的形狀，
不是「用一整個網頁管理記帳」的形狀。

### 為什麼排在 Slice 4 之前

Slice 4（分類管理 + 個人資料）要新增兩個頁面。先定骨架，那兩頁只做一次；
反過來就是同樣的版面工做兩次。

而且 Slice 4 已經談過的假設 B3、B4（分類分兩區、每區各一顆新增鈕）本來就是為
640px 單欄想的，寬版面下答案不一樣。那兩條假設在本步完成後重新確認。

### 範圍內

- 外殼改成「左側邊欄 + 右主區」，內容區加寬至 70rem。
- 導覽與帳本切換器從頂部水平列搬進側邊欄。
- 窄螢幕（< 900px）改用漢堡**浮動選單**。
- 首頁改成兩欄：左邊篩選與交易列表，右邊新增表單與帳戶餘額。
- 擴充 `global.css` 的設計 token：字級、行高、陰影、狀態色、間距、版面尺寸。
- 其餘四頁調整間距以適應新寬度。

### 範圍外

- **交易列表的日曆檢視**——開發者於 2026-08-26 提出，**延後至 Slice 5**，理由見 §8。
- **配色與主題**——主色維持 `#2563eb`。換色系與深色模式另開一步，時機未定（§8）。
- **列表改表格**——維持 `<ul><li>`。改表格會讓 15 條 e2e 全部失效，且畫面尚未定型（§8）。
- 首頁統計卡片——仍需後端彙總端點，維持「即將推出」。
- 任何後端變更、任何新套件、任何 API 介面變更。

## 2. 已定案的決策

四項決策皆於 2026-08-26 由開發者在提案頁上裁示。

### D1：側邊欄放導覽，帳本切換器放在側邊欄頂端

側邊欄由上而下是：站名 → 作用中帳本切換器 → 主導覽 → 分隔線 → 個人資料 / 登出。
頂列只放頁面標題。

**理由**：切換器決定其他每一個連結看到什麼資料，是讀導覽之前該先知道的事。
這正是 `AppHeader.tsx:33` 現有註解的理由，只是換個位置照做。

**知會過的替代方案**：（A）切換器放頂列——它會離導覽很遠，被排在視線末端。
（C）不要側邊欄只放寬——只要半天，但 Slice 4 之後是 6 個連結加切換器加登出，
頂列會換行；日後真要側邊欄，那半天等於白做。

### D2：首頁分兩欄，新增表單常駐右側欄

左主欄放篩選、交易列表、分頁；右側欄放新增表單與帳戶餘額。
低於斷點時退回單欄，且新增表單仍排在列表前面（與現況一致）。

**理由**：記帳是高頻動作，表單常駐可以少一次點擊。

**為什麼不把新增改成彈窗**：那會讓 `e2e/ui.ts:31` 的 `newTransactionForm()`
定位到的表單變成彈窗內容，5 條 e2e 要跟著改——與 SC-19 的第 4 條互斥。

### D3：窄螢幕用漢堡浮動選單，不是全屏抽屜

低於 900px 時側邊欄收起，頂列出現 ☰ 按鈕，點開後選單**浮在內容之上**。

要實作的行為，全部列出：

1. 點 ☰ 展開，再點一次收起。按鈕帶 `aria-expanded` 與 `aria-controls`。
2. 點選單以外的地方收起。
3. 按 Esc 收起，焦點退回 ☰ 按鈕。
4. 點任一連結後收起——頁面已經換了，選單不該留著。
5. **不做 focus trap。**

**第 5 點是重點。** 原本的疑慮（「鍵盤使用者跳不出去」）是**全屏抽屜**才有的問題：
抽屜是 modal，必須鎖焦點，鎖壞了就出不來。浮動選單不是 modal，鎖焦點反而製造那個問題。
開發者選 popover 正好繞開它。

**為什麼不用純 CSS 收成水平列**：開發者偏好選單形式，且未來若有多組選單（例如
帳本切換、使用者選單各自展開）這個模式擴充得下去。代價是多 3 到 4 小時與一組元件測試。

**最容易漏掉的一條是第 2 點。** 少了它，選單會蓋著內容不走，而使用者不會想到要
再點一次 ☰。必須有測試釘住。

### D4：只補結構性 token，主色不動

補進 `global.css`：字級階層、行高、陰影、狀態色（hover / focus / disabled）、
`--space-xl` 與 `--space-2xl`、側邊欄寬與頂列高。主色維持 `#2563eb`。

**為什麼不順便換色**：版面與配色同時變，出問題時分不出是哪一邊造成的。
配色是偏好，來回調整的時間不可預估，會把半天的工作拖成兩天。

**對未來不欠債**：顏色本來就全部收斂成 CSS 變數。未來要做主題（含深色模式）
只要覆寫變數那一層，元件一個都不用改。

## 3. 可驗證的成功條件

本步在 `phase-2-web-mvp.md §3` 沒有對應的成功條件——那裡的 SC 全是功能導向。
**提議新增 SC-19**，核可後同步寫入該檔 §3。

> **SC-19｜版面**
>
> 1. 1440px 寬時導覽在側邊欄，內容區不超過 70rem 且置中。
> 2. 首頁在寬螢幕分兩欄；低於 900px 退回單欄。
> 3. 375px 到 2560px 之間任何寬度都不出現橫向捲動。
> 4. **既有 15 條 e2e 一行都不改就全數通過。**

其餘驗收條件（不進 spec §3，屬本步內部）：

| #   | 驗收                                                                                              | 怎麼驗                                                |
| --- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 5   | 窄螢幕：☰ 開闔、點外面收起、Esc 收起且焦點回按鈕、點連結收起                                     | 元件測試 + 瀏覽器手動                                 |
| 6   | 既有 130 條元件測試只有 `AppHeader.test.tsx` 需要改寫（改名為 `AppShell.test.tsx`）；總數只增不減 | `pnpm test`（web ≥ 130）                              |
| 7   | 鍵盤 Tab 可依序走完側邊欄與內容，focus 看得見                                                     | 瀏覽器手動                                            |
| 8   | 全套指令綠                                                                                        | `pnpm lint / typecheck / test / build / format:check` |

### SC-19 第 4 條是本步的硬約束

e2e 對版面的相依只有三處，都已查證：

- 導覽用 `getByRole('link', { name })`——`e2e/ledgers.spec.ts:23` 等 5 處。
- 帳本切換器用 `getByLabel('作用中帳本')`——`e2e/ui.ts:17`。
- 站名用 `heading level 1`——`e2e/smoke.spec.ts:33`。

只要這三樣的無障礙名稱不變，搬到側邊欄不影響測試。

**浮動選單也不影響。** Playwright 用 `devices['Desktop Chrome']`，視窗固定 1280×720，
遠大於 900px 斷點，測試看到的永遠是展開的側邊欄。

## 4. 技術設計

### 外殼結構

> **2026-08-26 修正**：本節原先畫的是「站名在側邊欄、頂列顯示頁面標題」。
> 實作前查證發現頂列放頁面標題會與各頁自己的 `h2` 撞名，讓
> `getByRole('heading', { name })` 對到兩個而拋錯。改為站名放頂列、頂列不放
> 頁面標題。完整理由見 `tasks/phase-2f-plan.md` D5。下方是實際落地的結構。

```
App.tsx                            useDisclosure() 的狀態放在這一層
└── div.shell                      flex column, min-height 100vh
    ├── AppTopBar                  sticky top；全寬
    │   ├── button ☰               只在 < 900px 顯示；aria-expanded / aria-controls
    │   └── h1 站名                全站唯一的 h1，未登入時也在
    └── div.body                   flex row
        ├── AppSidebar             固定寬 14rem，sticky；只在已登入時渲染
        │   ├── LedgerSwitcher     label 維持「作用中帳本」
        │   ├── nav 主要導覽       首頁 / 帳本 / 帳戶（Slice 4 後 + 分類）
        │   └── footer            登出（Slice 4 後 + 個人資料）
        └── main.main > AppRoutes  max-width 70rem，置中
```

`AppHeader.tsx` 拆成 `AppSidebar.tsx` 與 `AppTopBar.tsx`。拆分的理由與原本
把頁首放在路由之外相同：導覽只該有一份實作，頁面一多，複製出來的那幾份遲早
會有一份漏掉新連結。

`useDisclosure` 的狀態放在 `App.tsx`：**觸發鈕在頂列、面板是側邊欄**，兩個元件
各持有一半，狀態只能放在它們共同的父層。這個 hook 不依賴任何 Provider，
所以不必為它多包一層元件。

### 浮動選單的開闔

抽成 `use-disclosure.ts`，負責開闔狀態、點外面關閉、Esc 關閉。
獨立成 hook 是為了 D3 提到的「未來多組選單」——第二組選單直接用同一個 hook。

不使用 `<dialog>`：那會變成 modal，與 D3 的第 5 點衝突。

### 新增的設計 token

| 類別 | 變數                                                                        |
| ---- | --------------------------------------------------------------------------- |
| 字級 | `--text-xs` / `--text-sm` / `--text-base` / `--text-lg` / `--text-xl`       |
| 行高 | `--leading-tight` / `--leading-normal`                                      |
| 陰影 | `--shadow-sm`（卡片）/ `--shadow-md`（浮動選單）                            |
| 狀態 | `--color-primary-hover` / `--color-focus-ring` / `--color-surface-hover`    |
| 間距 | `--space-xl` / `--space-2xl`                                                |
| 版面 | `--sidebar-width` / `--topbar-height` / `--content-max` / `--breakpoint-md` |

既有的 7 個顏色與 4 個間距**一個都不動**，避免現有畫面出現非預期的位移。

## 6. 測試策略

- **元件測試**：`AppSidebar.test.tsx` 新增四條（開闔、點外面、Esc、點連結）。
  `AppHeader.test.tsx` 改寫成新結構，斷言不變——它測的是「導覽連結指向正確路徑」，
  那件事與版面無關。
- **e2e**：**一行都不改**。它同時是本步的迴歸網——版面重整最可能弄壞的正是
  「連結還在不在、切換器還找不找得到」，而那三件事 e2e 全部釘住了。
- **不做視覺回歸測試**：畫面正在大改，現在釘住只會製造雜訊（沿用
  `phase-2e-web-e2e.md` §8 的立場）。
- **手動驗收**：375px / 900px / 1440px / 2560px 各看一次，確認無橫向捲動與斷點行為。

## 7. 界線（Always / Ask first / Never）

**Always**：改動前先完整 Read 目標檔案；每一步跑 `pnpm --filter @ledger/web typecheck`
與 `test`；保持三個 e2e 相依的無障礙名稱不變（導覽連結文字、「作用中帳本」、`h1` 站名）。

**Ask first**：任何新套件（本步預期為零）；任何 `features/` 底下的改動；
任何會讓 e2e 需要修改的決定。

**Never**：為了版面方便改動列表的 DOM 結構；用 CSS class 當測試選取器；
改後端；改既有的 7 個顏色與 4 個間距變數。

### 日曆檢視為什麼另立一步

開發者於 2026-08-26 提出：交易列表要有第二種形式——一個完整日曆，
點某一天就顯示那天的交易。三個理由讓它不適合放進 2f：

1. **與 SC-19 第 4 條互斥。** 做日曆一定要改 e2e，而本步的硬約束是「e2e 一行都不改」。
   混在一起，兩邊都驗不清楚。
2. **它可能要改後端。** 現有列表端點的 `limit` 上限是 100
   （`apps/api/src/transactions/transactions.service.ts:127`）。要顯示「每天小計」
   就得先拿到整月交易，超過 100 筆時數字會是錯的——**金額算錯比不顯示更糟**。
   正解是後端加一個月曆彙總端點，那屬 Ask first，要另立 spec。
3. **2f 剛好幫它把位置留好了。** 日曆檢視未來就是在左主欄上方加一組
   「列表 / 日曆」切換鈕。先做 2f 不會讓它變難，也不必回頭重做版面。
