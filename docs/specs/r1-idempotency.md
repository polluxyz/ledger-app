## 0. 假設

開發者 2026-11-17 回「同意」核可以下 8 條。

1. **範圍**：5 個端點。交易（含 AI 確認）、借還帳、代墊分帳、結清、免除欠款。接受欠款提議與退出帳本已有防重，不納入。
2. **機制**：新增 1 張通用的鍵表，和資源寫在同一個資料庫交易（schema 變更）。
3. **必填**：5 個端點都必須帶 `Idempotency-Key` header（HTTP 標頭）。缺少或格式錯誤回 400，不設過渡期。
4. **重送時**：
   - 同鍵同內容回 201，回傳同一筆。
   - 同鍵不同內容回 409。
   - 原本那筆已刪除時回 409，不重建。
   - 每次都重新檢查權限。
5. **換鍵時機**：
   - 手動表單開始新記帳時產生鍵，成功後換新。
   - AI 每筆草稿一把鍵。
   - 網路錯誤時保留原鍵。
   - 同內容的另一筆消費是新的鍵。
6. **鍵只存在網頁記憶體**：重新整理後是新鍵。
7. **保留**：鍵永久保留，刪除帳號時一起刪。
8. **AI 文案**：AI 網路錯誤的訊息改成「尚未確認，請重試」，不加其他提示。

## 1. 目標與成功樣貌

使用者按「送出」後網路斷了，畫面顯示失敗。這時他不知道伺服器有沒有記下。現在按重試會多記 1 筆。本步讓「同一次記帳意圖」不管送幾次，帳上都只出現 1 次。

做法：網頁替每次記帳意圖產生一把隨機鍵，送出時放在 header。後端把鍵和建立的紀錄寫在同一個資料庫交易。同一把鍵再來，後端不再寫入，直接回第一次那筆。

例子：我在「日常」帳本記「午餐 120 現金」。

1. 我按送出。伺服器寫入成功，但回應在路上斷了。表單顯示錯誤，內容還在。
2. 我按送出重試。網頁帶同一把鍵。
3. 後端認出這把鍵已經完成，回 201 和第一次那筆交易。表單照成功處理：清空、換新鍵。
4. 交易列表只有 1 筆「午餐 120」，現金只扣 120。
5. 我接著再記一筆一樣的「午餐 120 現金」。這是新的記帳意圖，網頁用新鍵，帳上出現第 2 筆。

AI 也一樣：AI 解析出 3 筆草稿，每筆各有一把鍵。我按「全部確認」，第 2 筆網路斷了。草稿 2 顯示「尚未確認，請重試」。我再按確認，第 2 筆只會記 1 次。

### 範圍外

- 重新整理頁面、重新解析、換裝置後重送：網頁會產生新鍵，當成新的記帳意圖。要涵蓋這些情況，要另外設計「草稿恢復」，而且要把帳務內容存進瀏覽器，本步不做（假設 6）。
- 編輯（PATCH）與刪除（DELETE）：重送一樣的修改或刪除，結果相同，不會多記錢。不加鍵。
- 不建立金錢紀錄的新增：建立對象、帳本人物、帳戶、分類、好友邀請。重送最多多一個名字，不影響餘額，不加鍵。
- `POST /debt-proposals/:id/accept`：已用 `PENDING` 條件更新，和寫入在同一個交易（`apps/api/src/debts/debt-proposals.service.ts:141`、`:425`）。
- `POST /ledgers/:ledgerId/leave`：已有成員鎖、同交易移除成員、Serializable 隔離（`apps/api/src/ledgers/ledger-leave.service.ts:117`、`:175`）。
- 鍵的到期清理排程：不做（假設 7）。
- 行動 App：尚未建立。App 建立時照本 spec 的 header 契約帶鍵。

## 3. 資料模型

新增 1 張表，需要 1 個 Prisma migration。不改現有的表。

```prisma
/// 防重複送出的鍵（R1）。和它建立的資源寫在同一個資料庫交易。
model IdempotencyKey {
  id           String               @id @default(uuid())
  userId       String
  key          String               // 小寫 UUID
  operation    IdempotencyOperation
  scopeId      String?              // 路徑上的 ledgerId 或 counterpartyId；沒有路徑參數的端點為 null
  requestHash  String               // "v1:" + SHA-256
  resultType   IdempotencyResultType
  resultId     String               // 指向 resultType 那張表，沒有資料庫外鍵
  createdAt    DateTime             @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, key])
}

enum IdempotencyOperation {
  TRANSACTION_CREATE
  DEBT_ENTRY_CREATE
  SPLIT_CREATE
  SETTLEMENT_CREATE
  COUNTERPARTY_FORGIVE
}

enum IdempotencyResultType {
  TRANSACTION   // 交易、結清
  DEBT_ENTRY    // 借還帳、免除欠款
  SPLIT         // 代墊分帳
}
```

- `resultType` 與 `resultId` 在搶鍵時還不知道。實作可以先寫暫時值、最後在同一個交易內更新，或讓這 2 欄可為 null。由 plan 決定，條件是提交後的列一定有結果。
- 沒有 `updatedAt`：鍵寫入後不再改（同一個交易內填結果不算）。
- 欄位最終寫法由 plan 定，不改上面的語意。

5 個端點的 request 多 1 個必填 header，body 與成功回應的格式不變。

| 端點                                   | 新增 header               | 新的回應                                                                                        |
| -------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------- |
| `POST /ledgers/:ledgerId/transactions` | `Idempotency-Key`（必填） | 400 `IDEMPOTENCY_KEY_INVALID`；409 `IDEMPOTENCY_KEY_REUSED`；409 `IDEMPOTENCY_RESOURCE_DELETED` |
| `POST /debt-entries`                   | 同上                      | 同上                                                                                            |
| `POST /splits`                         | 同上                      | 同上                                                                                            |
| `POST /ledgers/:ledgerId/settlements`  | 同上                      | 同上                                                                                            |
| `POST /counterparties/:id/forgive`     | 同上                      | 同上                                                                                            |

- 正常重送回 201，body 是同一筆資源用目前狀態重建的結果。
- 受影響的前端：`apps/web` 的 5 個呼叫處（W289、W290）。行動 App 尚未建立。
- `packages/shared`：header 名稱常數、3 個 `errorCode`（決策 370 (c)）。

## 5. 成功條件

API 端的 SC 用 API e2e（真的 PostgreSQL）驗證，進 CI。網頁端的 SC 用 Vitest 與 Playwright，進 CI。

**每一條防重的測試，都要斷言「資料庫裡的筆數」與「金額效果」，不能只看回應。** 金額效果指帳戶餘額、對象欠款、份額交易、差額交易、提議的筆數。

- **SC-IK1**（header 驗證）：5 個端點各測 4 種情況：沒帶、空字串、不是 UUID、2 個值。全部回 400 `IDEMPOTENCY_KEY_INVALID`，資料庫筆數不變。合法的大寫 UUID 可以用，存成小寫。
- **SC-IK2**（依序重送）：5 個端點各送 2 次同鍵同內容。2 次都回 201，資源 id 相同，金額效果只出現 1 次。
- **SC-IK3**（並發重送）：5 個端點各用同一把鍵同時送 2 個請求（`Promise.all`）。2 個都回 201、id 相同，金額效果只出現 1 次。沒有 500。
- **SC-IK4**（同鍵不同內容）：
  1. 同端點、改金額 → 409 `IDEMPOTENCY_KEY_REUSED`。
  2. 同內容、換成另一個端點 → 409 同上。
  3. 同內容、換成另一本帳本或另一個對象 → 409 同上，不回傳原帳本的資源。
  4. 以上都不新增紀錄，原紀錄不變。
- **SC-IK5**（同內容不同鍵）：同一筆內容用 2 把鍵送，建立 2 筆，金額效果 2 次。合法的重複消費不會被擋。
- **SC-IK6**（原紀錄已刪除）：5 個端點各建立後刪除結果資源（交易、結清、分帳、借還紀錄），再用同鍵同內容送 → 409 `IDEMPOTENCY_RESOURCE_DELETED`，沒有新紀錄，被刪的沒有被還原。
- **SC-IK7**（回滾）：
  1. 第 1 次因業務錯誤失敗（例如還款超過餘額）→ 鍵表沒有這把鍵。條件改變後用同鍵同內容送 → 正常建立 1 筆。
  2. 在寫入途中強制丟錯（測試注入）→ 鍵、交易、份額、差額、提議、AI 新分類全部不存在。
- **SC-IK8**（提交後回應失敗）：讓重建回應的讀取在提交後丟錯（單元或整合測試注入）→ 鍵與資源仍在。之後用同鍵重送 → 201，id 相同，只有 1 筆。
- **SC-IK9**（隔離）：
  1. 使用者 B 用和 A 相同的鍵字串，送 B 自己帳本的請求 → B 建立自己的紀錄，回應不含 A 的任何資料。
  2. A 建立後被移出帳本，再用同鍵重送 → 403 或 404，回應不含原資源內容。
  3. 共享帳本中 A 被降為 viewer 後重送 → 403。
- **SC-IK10**（免除欠款）：A 免除對象 X 的欠款成功。之後 X 又新增一筆欠款。用原鍵重送免除 → 201 回原本那筆免除紀錄，新欠款沒有被免除。
- **SC-IK11**（契約）：
  1. OpenAPI 的 5 個端點都列出必填的 `Idempotency-Key` header 與 3 個新錯誤。
  2. 從 `CORS_ORIGIN` 送帶 `Idempotency-Key` 的預檢請求 → 回應放行這個 header。
  3. 其他端點不受影響：不帶 header 照常成功。
- **SC-IK12**（手動表單，Vitest）：`TransactionForm`（交易、分帳）、`DebtEntryForm`、`SettlementForm`、免除欠款對話框各測：
  1. 送出時 header 帶鍵。
  2. 網路錯誤後重試，鍵相同、body 相同。
  3. 成功後在同一個表單記下一筆，鍵不同。
  4. 重新開表單，鍵不同。
- **SC-IK13**（AI，Vitest）：
  1. 解析出 N 筆草稿，N 把鍵互不相同。
  2. 同一筆草稿的單筆確認、全部確認、打開草稿表單送出，用同一把鍵。
  3. 網路錯誤 → 草稿顯示「尚未確認，請重試」，草稿與鍵保留。400／409 業務錯誤照原文案。
  4. 重新解析後是新鍵。
- **SC-IK14**（回應遺失，Playwright）：用 `route.fetch()` 把請求送到伺服器，再丟掉回應，模擬「伺服器已寫入但回應遺失」。
  1. 手動表單：使用者按重試 → 列表只有 1 筆，帳戶餘額只扣 1 次。
  2. AI 全部確認：第 2 筆回應遺失，按確認重試 → 3 筆各只有 1 次。
- **SC-IK15**（產生鍵）：在不是安全環境（沒有 `crypto.randomUUID`）時仍能產生合法的 UUID v4。
- **SC-IK16**（回歸）：`pnpm lint`、`typecheck`、`test`、`build`、`format:check` 全綠；兩套 e2e 全綠。現有呼叫這 5 個端點的 API e2e 改成帶 header，斷言不放寬。

## 6. 測試策略

- **先寫、先紅**（協調者）：SC-IK9（隔離）與 SC-IK3（並發）。前者是資料隔離的防線，後者是這個機制最容易做錯的地方。
- API e2e：SC-IK1～SC-IK7、SC-IK9～SC-IK11。用 Jest 對 `.env.test` 的資料庫跑。並發測試要真的同時送，不能用 mock。
- API 單元測試：共用服務的搶鍵、比對、P2002 處理、雜湊正規化（欄位順序不同的同一個物件，雜湊相同）。SC-IK8 的注入放這層或整合測試。
- Web Vitest：SC-IK12、SC-IK13、SC-IK15。
- Playwright：SC-IK14。照現有 Web e2e 的設定，不改 CI、不加套件。
- 既有測試：API e2e 中呼叫這 5 個端點的地方改成帶 header（建議加測試輔助函式）。Web 既有測試的斷言不改，只補 header。

## 7. 界線

- **Always**：搶鍵與業務寫入在同一個交易；查鍵一定限定 `userId`；重送一定重驗權限；每條防重測試都斷言筆數與金額效果。
- **Ask first**：改 5 個端點以外的端點；把鍵存進瀏覽器的 `localStorage` 或其他持久儲存；加清理排程；改 CORS 設定；加套件。
- **Never**：用金額、日期、備註相同來判斷重複；把完整回應或原始請求存進鍵表；鍵的唯一衝突以外的 P2002 被吞掉；重送時重建或還原已刪除的資源；`api-client` 每次請求自己產生新鍵。

## 10. 核可時確認的項目

1. **2 個新錯誤的畫面文字**（W292）：同鍵不同內容顯示「已記錄過」，原紀錄已刪除顯示「這筆已刪除」。同意，或給別的字。
2. **失敗後改內容再送**（W289 (e)）：鍵不換。第 1 次已寫入時會看到「已記錄過」，不會多一筆；要記第 2 筆就關掉表單重開。同意，或改成「改了內容就換新鍵」（換新鍵會在第 1 次其實已寫入時多記 1 筆）。
