## 4. 設計決策

D1～D4 已於 spec §2 核可，此處不重述。以下是實作階段新發現、**需要一併核可**的四項。

### D5 — 站名放頂列，頂列不放頁面標題（偏離提案頁 mockup）

**提案頁的 mockup 畫的是**：站名在側邊欄，頂列顯示頁面標題（「首頁」）。
實作前查證後發現那樣做會壞掉。

**壞在哪**：每一頁都已經有自己的 `h2` 標題——`AccountsPage.tsx:42`「帳戶」、
`LedgersPage.tsx:23`「帳本」、`LedgerDetailPage.tsx:162` 帳本名稱。
頂列再放一次同樣的字，`getByRole('heading', { name })` 會同時對到兩個而拋錯。
直接受害的是 `AppHeader.test.tsx:52` 與 `e2e/ledgers.spec.ts:127`——
**後者會讓 SC-19 第 4 條當場失守。**

**改成**：頂列在所有狀態下都存在，而且只做兩件事——顯示站名（全站唯一的 `h1`），
以及在窄螢幕顯示 ☰。頁面標題留在各頁自己的 `h2`，一個字都不動。

| 狀態        | 頂列      | 側邊欄           | 內容       |
| ----------- | --------- | ---------------- | ---------- |
| 未登入      | 站名      | 不渲染           | 置中窄欄   |
| 已登入 · 寬 | 站名      | 切換器 + 導覽    | 兩欄或單欄 |
| 已登入 · 窄 | 站名 + ☰ | 收起，點 ☰ 浮出 | 單欄       |

**這樣有三個好處**：`h1` 在任何狀態下都只有一個實例（`e2e/smoke.spec.ts:33`
與 `AppHeader.test.tsx:45` 都靠它）；不必發明一套「頁面把標題傳給外殼」的機制；
5 個頁面元件一個都不用改。

**代價**：桌機的頂列比 mockup 空。若日後覺得浪費，那裡是放「新增交易」快捷鈕的
天然位置——但那是新功能，不在本步。

**替代方案（不選）**：各頁移除 `h2`，改由頂列統一顯示標題。
`LedgerDetailPage` 的標題是帳本名稱、會動態變化，靜態的路由對照表處理不了，
得引入一個 title context。改動範圍是 5 個頁面元件加一套新機制，
換到的只是「標題往上移了 40px」。

### D6 — 一份 DOM，用 CSS 斷點切換形態，不用 `matchMedia`

側邊欄無論寬窄螢幕都渲染同一份 DOM，由 CSS 媒體查詢決定它是固定欄還是浮動選單。

**理由**：少一個狀態來源。用 `matchMedia` 的話，「現在是窄螢幕嗎」會同時存在於
CSS 與 JS 兩處，兩邊的斷點值遲早會分岔。

**附帶好處**：jsdom 不套用 CSS，所以元件測試裡側邊欄永遠「看得見」。
既有 `AppHeader.test.tsx` 對導覽連結的斷言不必模擬任何媒體查詢就能通過。

**桌機時開闔狀態沒有意義但也無害**——CSS 強制側邊欄顯示，`open` 與否不影響畫面。

### D7 — `use-disclosure` 的介面

```ts
const { isOpen, toggle, close, triggerProps, panelProps } = useDisclosure();
```

hook 負責三件事：開闔狀態、`document` 上的點外面關閉、Esc 關閉並把焦點退回觸發鈕。
`triggerProps` 提供 `aria-expanded` 與 `aria-controls`，`panelProps` 提供 `id`。

**獨立成 hook 而不是寫死在 `AppSidebar` 裡**：D3 提到未來可能有多組選單
（帳本切換、使用者選單各自展開）。第二組直接用同一個 hook，不必再解一次
「點外面要關」這個問題。

**不使用 `<dialog>`**：那會變成 modal，與 D3 第 5 點（不做 focus trap）衝突。

### D8 — 新增的 token 一律是純加法

既有的 7 個顏色與 4 個間距變數**一個都不改**，只增加新的。

**理由**：改既有變數會讓每一頁的間距同時位移，而本步已經在動版面——
兩種變化混在一起，看到跑版時分不出是哪一邊造成的。

## 6. 風險與對策

| 風險                                  | 對策                                                                                          |
| ------------------------------------- | --------------------------------------------------------------------------------------------- |
| **e2e 變紅**（SC-19 第 4 條失守）     | 三個相依的無障礙名稱不動：導覽連結文字、`aria-label="作用中帳本"`、`h1` 站名。D5 就是為此而改 |
| 站名出現兩個 `h1`                     | 站名只在 `AppTopBar` 渲染一次，側邊欄不放。Step 3 的測試釘住                                  |
| 浮動選單開著卻關不掉                  | D7 的「點外面關閉」。這條最容易漏，`AppSidebar.test.tsx` 專門測它                             |
| Esc 關閉後焦點掉到 `<body>`           | hook 負責把焦點退回觸發鈕，測試斷言 `document.activeElement`                                  |
| 表單欄位在窄側欄裡被撐爆              | `TextField` / `Select` 的容器已有 `min-width: 0`（Slice 3 的教訓）。首頁側欄只用這兩個元件    |
| 改 token 造成既有畫面位移             | D8：純加法，既有變數一個都不動                                                                |
| 未登入頁面誤渲染側邊欄而打出 401 請求 | 側邊欄只在 `isAuthenticated` 時渲染，與現行 `AppHeader` 的判斷一致                            |

模組轉譯較慢。但這只是推測，沒有證據——失敗當下的 trace 已被後續執行覆蓋。

`retries: 0` 是刻意的（`phase-2e-web-e2e.md` D8：不穩定就當 bug 修）。
