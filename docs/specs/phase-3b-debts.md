## 1. 目標與成功樣貌

讓使用者記錄「**我跟這個人之間，現在誰欠誰多少**」，並讓帳戶餘額反映實際收付。

本步完成後，使用者可以：

1. 對一個人記借出、借入、還款。還款的方向由系統依目前誰欠誰決定（修訂 1）。餘額自動抵銷，不必管「這筆還的是哪一筆」。
2. ~~記「對方幫我付了我那份」~~：修訂 1 從畫面拿掉，之後與代墊一起設計（決策 49）。後端能力保留。
3. 記還款時勾「以此結清」，讓餘額歸零；差幾塊或多給幾塊，差額記下來，不另外產生交易。
4. 對方欠我時「免除剩餘」。
5. 看每個人的往來餘額，以及和某個人的全部往來紀錄與當時的累計餘額。
6. 記帳前先看到現況：「目前小明欠你 $120；記完後小明欠你 $9」。

### 範圍內

- 對象、往來紀錄、結清與免除的調整紀錄。
- 5 種往來與交易的對應（§4.1）；「對方幫我付」產生一筆不經過帳戶的支出。
- 交易回應帶出對象名字（只給往來紀錄的擁有者）。
- 移除逐筆債務版的資料表與端點。
- `@ledger/shared` 型別與錯誤碼；單元測試與 e2e。
- Web 畫面見 `phase-3b1-web.md`。

### 範圍外（見 §9）

- 多人分帳（一餐三個人各付各的份）。這次只做單人代付。
- 對象合併。
- 3b-2 連動的細節（§11 只記方向）。
- 多幣別。

## 3. 概念與規則

### 3.1 名詞

| 名詞     | 意思                                                              |
| -------- | ----------------------------------------------------------------- |
| 對象     | 記帳時的另一個人。屬於記帳者，只存名字                            |
| 往來紀錄 | 記帳者與對象之間的一次借、還、代付，或一筆調整                    |
| 調整紀錄 | 結清差額、免除這兩種。只改往來餘額，不產生交易                    |
| 往來餘額 | 所有未刪除往來紀錄的 `delta` 加總。正數＝對方欠我，負數＝我欠對方 |
| `delta`  | 一筆往來紀錄對往來餘額的影響，有正負號                            |

### 3.2 7 種往來紀錄

| 種類（`kind`） | 中文       | `delta` | 產生的交易                    | 帳戶 |
| -------------- | ---------- | ------- | ----------------------------- | ---- |
| `LEND`         | 借出       | ＋金額  | `LEND`                        | −    |
| `BORROW`       | 借入       | −金額   | `BORROW`                      | ＋   |
| `COLLECT`      | 對方還我   | −金額   | `COLLECT`                     | ＋   |
| `REPAY`        | 我還對方   | ＋金額  | `REPAY`                       | −    |
| `PAID_FOR_ME`  | 對方幫我付 | −金額   | `EXPENSE`（有分類、不填帳戶） | 不變 |
| `SETTLEMENT`   | 結清差額   | 見 §3.3 | 無                            | 不變 |
| `FORGIVE`      | 免除       | −餘額   | 無                            | 不變 |

前 4 種都可以選「不記入帳本」（`record: null`），這時只記往來、不產生交易。`PAID_FOR_ME` 一定要產生支出交易。

`COLLECT`、`REPAY` 是**存下來的**種類。使用者送的是 `REPAYMENT`，由後端依餘額決定存成哪一種（§3.2.1）。

### 3.2.1 還款（修訂 1，決策 46～48、50）

記 `REPAYMENT`，金額 `a`：

1. 鎖住對象，讀出目前往來餘額 `b`。
2. `b = 0` → `409 NOTHING_TO_REPAY`。
3. `b > 0` → 存成 `COLLECT`（`delta = −a`）；`b < 0` → 存成 `REPAY`（`delta = +a`）。
4. 沒帶 `settle` 且 `a > |b|` → `409 REPAYMENT_EXCEEDS_BALANCE`。帶了 `settle: true` 就照 §3.3 結清。
5. 產生的交易型別跟著存下來的種類（`COLLECT` 或 `REPAY`），帳戶標籤也跟著方向。

| 目前餘額    | 還款 | 以此結清 | 結果                                 |
| ----------- | ---- | -------- | ------------------------------------ |
| 小明欠我 93 | 90   | 否       | `COLLECT` −90，還欠 3                |
| 小明欠我 93 | 90   | 是       | `COLLECT` −90＋`SETTLEMENT` −3，兩清 |
| 小明欠我 93 | 95   | 是       | `COLLECT` −95＋`SETTLEMENT` +2，兩清 |
| 小明欠我 93 | 95   | 否       | `409 REPAYMENT_EXCEEDS_BALANCE`      |
| 我欠小明 40 | 40   | 否       | `REPAY` +40，兩清                    |
| 兩清        | 任意 | 任意     | `409 NOTHING_TO_REPAY`               |

修改與刪除不做這些檢查（決策 48）：改一筆 `COLLECT` 的金額讓餘額翻轉也照存，種類不變。

### 3.3 以此結清

記 `REPAYMENT` 時帶 `settle: true`：

1. 先寫入這筆還款，算出新的往來餘額 `b`。
2. `b ≠ 0` 就再寫一筆 `SETTLEMENT`，`delta = −b`，讓餘額歸零；`b = 0` 就不寫。
3. 兩筆在同一個資料庫交易裡。

差額的意義：`SETTLEMENT.delta` 正數＝對我有利（對方多給、或我少付），負數＝對我不利。例：小明欠我 93，還 90 並結清 → `SETTLEMENT.delta = −3`，我少收 3。

### 3.4 免除

只在往來餘額 `b > 0` 時可以做，寫一筆 `FORGIVE`，`delta = −b`。`b ≤ 0` 回 `409 NOTHING_TO_FORGIVE`。

### 3.5 誰能做什麼

| 角色         | 能做                                                       | 不能做                                                                    |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------- |
| 對象的擁有者 | 讀取、改名、刪除（無紀錄時）、記往來、改與刪往來紀錄、免除 | —                                                                         |
| 其他任何人   | 無                                                         | 讀取或操作任何對象、往來紀錄（`404`）                                     |
| 帳本成員     | 看到記在該帳本的借還交易與代付支出（決策 13）              | 從交易追到背後的往來：交易回應的 `debt` 只對擁有者有值，其他成員是 `null` |

另外兩條原有規則照樣適用：把交易記進某帳本要有 EDITOR 以上且帳本未封存；指定的帳戶必須屬於呼叫者。

## 4. 資料模型（Prisma）

> 依 `CLAUDE.md` §14，schema 變更屬於「先說明再做」。開發者 2026-09-24 已同意假設清單（含清掉 dev 測試資料）；migration 的手寫 SQL 在 plan 列出。

### 4.1 交易

`TransactionType` 不變（7 種）。借還的 4 種沒有分類。`PAID_FOR_ME` 產生的是一般 `EXPENSE`：有分類、`accountId` 為 null，即使帳本是連動帳本也一樣——這是唯一允許連動帳本的支出不填帳戶的情況，而且只能從往來帳端點建立。

### 4.2 新增與移除的 model

移除：`Debt`、`DebtPayment`、`DebtDirection`。

```prisma
enum DebtEntryKind {
  LEND
  BORROW
  COLLECT
  REPAY
  PAID_FOR_ME
  SETTLEMENT
  FORGIVE
}

/// 記帳者的一個往來對象。只存名字（決策 33）。
model Counterparty {
  id        String    @id @default(uuid())
  ownerId   String
  name      String    // 去掉前後空白，1～100 字
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt

  owner   User        @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  entries DebtEntry[]

  @@unique([ownerId, name])
}

/// 一筆往來紀錄。往來餘額 = Σ 未刪除的 delta（決策 34）。
model DebtEntry {
  id             String        @id @default(uuid())
  counterpartyId String
  kind           DebtEntryKind
  /// 對往來餘額的影響，有正負號，不為 0。正負號與 kind 的對應見 spec §3.2，由 CHECK 約束保證。
  delta          Int
  date           DateTime
  note           String?
  /// 產生的交易。調整紀錄與「不記入帳本」為 null。
  transactionId  String?       @unique
  deletedAt      DateTime?
  createdAt      DateTime      @default(now())
  updatedAt      DateTime      @updatedAt

  counterparty Counterparty @relation(fields: [counterpartyId], references: [id], onDelete: Cascade)
  transaction  Transaction? @relation(fields: [transactionId], references: [id], onDelete: Restrict)

  @@index([counterpartyId, deletedAt])
}
```

### 4.3 migration 手寫的部分

1. 刪除逐筆債務版產生的交易（決策 45）：`DELETE FROM "Transaction" WHERE type IN ('LEND','BORROW','COLLECT','REPAY')`，在 drop `Debt`、`DebtPayment` 之前執行。
2. `DebtEntry` 的 CHECK：`delta <> 0`；`kind IN ('LEND','REPAY')` 時 `delta > 0`；`kind IN ('BORROW','COLLECT','PAID_FOR_ME','FORGIVE')` 時 `delta < 0`；`kind IN ('SETTLEMENT','FORGIVE')` 時 `"transactionId" IS NULL`；`kind = 'PAID_FOR_ME'` 時 `"transactionId" IS NOT NULL`。
3. `Counterparty` 的 CHECK：`length(trim(name)) BETWEEN 1 AND 100` 且 `name = trim(name)`。

### 5.1 對象

| `GET /counterparties`               | 我的對象清單，含往來餘額。排序：餘額不為 0 的在前，其次依名字。`?page=&limit=`           |

| `DELETE /counterparties/{id}`       | 有未刪除的往來紀錄回 `409 COUNTERPARTY_HAS_ENTRIES`                                      |
| `GET /counterparties/{id}/entries`  | 往來紀錄，依日期新到舊，每筆附 `balanceAfter`（寫入這筆之後的累計餘額）。`?page=&limit=` |
| `POST /counterparties/{id}/forgive` | 免除剩餘（§3.4）                                                                         |

```ts
// 對象
{ id, name, balance: number, createdAt, updatedAt }
```

### 5.2 往來紀錄

| 方法與路徑                  | 說明                                                   |
| --------------------------- | ------------------------------------------------------ |
| `POST /debt-entries`        | 記一筆往來。body 見下                                  |
| `PATCH /debt-entries/{id}`  | 改 `amount`、`date`、`note`（決策 41）。調整紀錄不能改 |
| `DELETE /debt-entries/{id}` | 軟刪除，連同交易（決策 42）                            |

```ts
// POST /debt-entries
{
  // 二選一：既有對象，或名字（不存在就建立，決策 33）
  counterparty: { id: string } | { name: string };
  kind: 'LEND' | 'BORROW' | 'REPAYMENT' | 'PAID_FOR_ME';  // 修訂 1：COLLECT、REPAY 改由後端依餘額決定（§3.2.1）
  amount: number;          // 正整數；delta 的正負號由 kind（還款則由餘額）決定
  date: string;            // ISO 8601
  note?: string;
  record: { ledgerId: string; accountId?: string } | null;  // null = 不產生交易；PAID_FOR_ME 不可為 null、不可帶 accountId
  categoryId?: string;     // PAID_FOR_ME 必填，須為該帳本的支出分類；其他種類不可帶
  settle?: boolean;        // 只有 REPAYMENT 可以帶（§3.3）
}

// 回應
{
  counterparty: { id, name, balance, ... };   // 寫入後的狀態
  entries: DebtEntry[];                        // 這次寫入的 1 或 2 筆（含結清差額）
}

// 往來紀錄
{
  id, counterpartyId, kind, delta, date, note,
  transactionId: string | null,
  balanceAfter?: number,   // 只在 GET /counterparties/{id}/entries 回傳
  createdAt, updatedAt,
}
```

`record` 的規則與一般交易相同：帳本需 EDITOR 以上且未封存；連動帳本必填 `accountId`、非連動帳本不可填（`PAID_FOR_ME` 例外，一律不可填）；帳戶必須屬於呼叫者。**`record` 必填**（物件或 `null`），不再有「省略就沿用」的隱含行為。

### 5.3 交易端點的調整（既有端點）

- `POST` / `PATCH /ledgers/{id}/transactions` 的 `type` 仍只接受 `EXPENSE`、`INCOME`、`TRANSFER`。
- `PATCH` / `DELETE` 一筆由往來紀錄產生的交易（**含 `PAID_FOR_ME` 的支出**）→ `409 DEBT_TRANSACTION_READ_ONLY`。判斷依據改成「有沒有往來紀錄指向它」，不再只看型別。
- 交易回應：`debtId` 改成 `debt: { entryId, counterpartyId, counterpartyName } | null`（決策 43）。
- `DELETE /ledgers/{id}`：帳本內有任何往來紀錄產生的交易（含已軟刪除的）→ `409 LEDGER_HAS_DEBT_TRANSACTIONS`。

### 5.4 錯誤碼

新增：`COUNTERPARTY_NAME_TAKEN`、`COUNTERPARTY_HAS_ENTRIES`、`NOTHING_TO_FORGIVE`、`DEBT_ENTRY_NOT_EDITABLE`（改調整紀錄）。
保留：`DEBT_TRANSACTION_READ_ONLY`、`LEDGER_HAS_DEBT_TRANSACTIONS`。
移除：`DEBT_OVERPAYMENT`、`DEBT_NOT_OPEN`、`DEBT_NOT_FORGIVABLE`（逐筆債務版專用）。
修訂 1 新增（皆為 409）：`NOTHING_TO_REPAY`（餘額為 0 時還款）、`REPAYMENT_EXCEEDS_BALANCE`（新增的還款會讓欠款方向反過來）。

## 6. 可驗證的成功條件

- **SC-L1**：對「小明」借出 120（現金）、再向「小明」借入 111（現金）→ 小明的往來餘額 9；現金 −9；交易列表有 `LEND` 120 與 `BORROW` 111。
- **SC-L2**：`counterparty: { name: ' 小明 ' }` 與 `{ name: '小明' }` 寫到同一個對象；`GET /counterparties` 只有一列。
- **SC-L3**（修訂 1 改寫）：小明欠我 9，記 `REPAYMENT` 20、不結清 → `409 REPAYMENT_EXCEEDS_BALANCE`，什麼都沒寫；同樣金額帶 `settle: true` → `COLLECT` −20＋`SETTLEMENT` +11，餘額 0。
- **SC-L4**：小明欠我 93，記 `REPAYMENT` 90 並 `settle: true` → 回應有 2 筆紀錄（`COLLECT` −90、`SETTLEMENT` −3），餘額 0，現金 +90，只產生 1 筆交易。還 95 並結清 → `SETTLEMENT` +2。
- **SC-L5**：「對方幫我付」400，分類餐飲 → 往來餘額 −400；帳本多一筆 `EXPENSE` 400、分類餐飲、帳戶 null（即使是連動帳本）；帳戶餘額不變。`categoryId` 缺少、帶了 `accountId`、或 `record: null` → `400`。
- **SC-L6**：免除：餘額 50 → 寫一筆 `FORGIVE` −50，餘額 0，沒有交易；餘額 ≤ 0 → `409 NOTHING_TO_FORGIVE`。刪除那筆 `FORGIVE` → 餘額回到 50。
- **SC-L7**：改往來紀錄的金額 → 對應交易的金額一起改、帳戶餘額跟著變；改 `SETTLEMENT` 或 `FORGIVE` → `409 DEBT_ENTRY_NOT_EDITABLE`。
- **SC-L8**：刪除往來紀錄 → 紀錄與交易都軟刪除，帳戶餘額與往來餘額回到寫入前。
- **SC-L9**：`/transactions` 端點無法建立借還型別（`400`）；`PATCH`／`DELETE` 借還交易或「對方幫我付」的支出 → `409 DEBT_TRANSACTION_READ_ONLY`。
- **SC-L10**：帳本內有往來紀錄產生的交易（含代付支出）→ 真刪回 `409 LEDGER_HAS_DEBT_TRANSACTIONS`；封存照常。
- **SC-L11**：`record` 指到不是成員的帳本 → `404`；只有 VIEWER → `403`；別人的帳戶 → `404`；封存帳本 → `409 LEDGER_ARCHIVED`。任一失敗時，對象（若是新名字）、往來紀錄、交易都不會留下。
- **SC-L12**：共享帳本的其他成員看得到借還交易與代付支出，但交易回應的 `debt` 是 `null`；讀取別人的對象或往來紀錄 → `404`。
- **SC-L13**：往來紀錄列表的 `balanceAfter` 依日期由舊到新累加；同一天依建立時間。
- **SC-L14**：對象改名撞名 → `409 COUNTERPARTY_NAME_TAKEN`；有紀錄時刪除 → `409 COUNTERPARTY_HAS_ENTRIES`；紀錄全刪光後可以刪除。
- **SC-L15**：交易回應對擁有者帶 `debt.counterpartyName`（「小明」）。
- **SC-L16**：`pnpm lint / typecheck / test / build / format:check` 與兩套 e2e 全綠；migration 進版控且重跑無 pending。

修訂 1 新增：

- **SC-L17**：小明欠我 100，記 `REPAYMENT` 30（現金）→ 存成 `COLLECT` −30、交易型別 `COLLECT`、現金 +30、餘額 70。我欠小華 50，記 `REPAYMENT` 50（現金）→ 存成 `REPAY` +50、交易型別 `REPAY`、現金 −50、餘額 0。
- **SC-L18**：餘額 0 的對象，或用新名字記 `REPAYMENT` → `409 NOTHING_TO_REPAY`；新名字的對象不會被建立。
- **SC-L19**：`kind: 'COLLECT'` 或 `'REPAY'` → `400`。`settle` 帶在 `REPAYMENT` 以外的種類 → `400`。

## 10. 界線（Always / Ask first / Never）

- **Always**：往來餘額一律算出；借還交易的資金方向只由型別決定；`delta` 的正負號由 kind 決定並有 CHECK 約束；授權測試先於實作。
- **Ask first**：任何放寬 §3.5 的改動；讓一般交易端點能改往來紀錄產生的交易。
- **Never**：讓 `/transactions` 端點產生或修改借還交易與代付支出；在前端計算往來餘額；把往來紀錄或對象名字回傳給擁有者以外的人。
