# Spec：階段二 (2d) — 帳本類型（私人 / 共享）

> 狀態：**已實作，待驗收**（2026-08-23）
> 依據：2026-08-23 於 2b Slice 2 Step 2 完成後提出的需求變更，逐題定案，詳見 §2。
> 定位：**純後端小步**。2b Slice 2 的 Step 3（建立帳本）與 Step 6（成員管理）必須排在本步之後，否則會建出即將被丟棄的畫面。
> 執行順序：2b Slice 2 Step 0～2（已完成，PR #26）→ **本步** → 2b Slice 2 Step 3 之後各步。

---

## 1. 目標與成功樣貌

讓使用者在**建立帳本時**就決定它是「私人」還是「共享」，並讓這個選擇之後不可更改。

現況是帳本沒有類型，差別只在成員數：一個人就是私人，加了人就是共享。使用者建完帳本，不會知道「這本可以找人一起記」——那個入口埋在明細頁裡太深。而且「隨時可以加人」意味著一本原本很私密的帳本，可能在使用者沒有心理準備的情況下被分享出去。

### 範圍內

- `Ledger` 新增 `kind` 欄位（`PERSONAL` / `SHARED`），**建立後不可變更**。
- 私人帳本**禁止加入成員**（後端強制，不只是畫面上不給按）。
- 既有帳本的資料遷移（依目前成員數判定）。
- `@ledger/shared` 型別與兩個新錯誤碼。
- 單元測試與 e2e 測試。

### 範圍外

- **前端畫面**。本步為純後端，UI 併入 2b Slice 2 的 Step 3 與 Step 6。
- **複製交易到其他帳本**。「私人想變共享」要靠新建帳本再把交易搬過去，該功能尚未存在，另立步驟（見 §8）。
- **好友清單**。加成員目前只認已註冊的 email，真正的好友系統屬階段三。
- 依 `kind` 篩選帳本清單的查詢參數（見 §2 決策 8）。

## 2. 已定案的決策

| #   | 決策                                                            | 理由摘要                                                                         |
| --- | --------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 1   | 欄位名為 `kind`，值 `PERSONAL` / `SHARED`                       | 不用 `type`，避免與交易的 `type`（EXPENSE / INCOME / TRANSFER）混淆              |
| 2   | **建立後不可互轉**                                              | 開發者定案。轉換會讓「這本帳本誰看得到」在事後改變，而使用者未必察覺             |
| 3   | 私人帳本加成員回 **409** `PERSONAL_LEDGER_CANNOT_SHARE`         | 不是權限不足（owner 本人也不行），是帳本目前的狀態不允許。專屬錯誤碼才說得出原因 |
| 4   | 共享帳本**可以只剩一個成員**                                    | 決策 2 的必然結果。其他人退出後它仍是共享帳本，不會自動變回私人                  |
| 5   | 建立共享帳本時**可以先不加人**                                  | 對方可能還沒註冊，不該因此卡住建立                                               |
| 6   | 成員退出一律允許                                                | 擋下等於把人困在別人的帳本裡。原有「最後一位 owner 不能退出」的規則不變          |
| 7   | `kind` 省略時預設 `PERSONAL`                                    | 既有的 API 呼叫者不會壞；「沒特別說」時預設較保守的那一邊                        |
| 8   | `GET /ledgers` **不加**依 `kind` 篩選的參數                     | 帳本數量少，前端拿到清單自己分組即可——那是呈現，不是業務邏輯                     |
| 9   | 私人帳本的 `GET /members` **照常開放**                          | 永遠只回自己一筆。關掉它會讓前端多一個分支，換來的好處是零                       |
| 10  | `kind` 與 `tracksBalance` **正交**，四種組合都允許              | 共享＋連動是家庭帳本，共享＋不連動是出遊分帳，兩種都合理                         |
| 11  | 遷移依**目前成員數**判定：超過 1 人設 `SHARED`，其餘 `PERSONAL` | 這是唯一能從既有資料推得的答案，也與規則本身一致                                 |

### 為什麼不能繼續用成員數推導

決策 2 與 4 一起讓「用成員數推導」失效：一本共享帳本可能只有一個成員（其他人都退出了），這時它仍然必須是共享帳本。成員數看不出這件事，所以需要一個真正的欄位。

這不違反 `CLAUDE.md` §6——該條禁止的是「兩套獨立資料表」，同一張表加一個判別欄位不在此列。但它確實偏離了原文「差別在於成員數與角色」的說法，`CLAUDE.md` 需一併更新。

### 已知且接受的代價

**私人帳本想變共享，在「複製交易」做出來之前無解。** 使用者只能新建一本共享帳本重新開始，舊帳本的交易帶不過去。

這與「初始餘額建立後不可更改」是同一個形狀的取捨（見 `phase-2c-accounts.md` §8）：規則本身是對的，但補救手段還沒做。差別在於初始餘額打錯是失誤，而選錯帳本類型比較可能發生——使用者一開始未必知道自己會不會想分享。

**因此複製交易的優先度高於它在延後清單上的位置**，見 §8。

## 3. 可驗證的成功條件

- **SC-D1**：`POST /ledgers` 可指定 `kind`；省略時為 `PERSONAL`。回應含 `kind`。
- **SC-D2**：`kind` 建立後不可變更——`PATCH /ledgers/{id}` 帶著它回 **400** `LEDGER_KIND_IMMUTABLE`，且值真的沒被改到。
- **SC-D3**：對 `PERSONAL` 帳本 `POST /ledgers/{id}/members` 回 **409** `PERSONAL_LEDGER_CANNOT_SHARE`，且該使用者沒有被加進去。owner 本人呼叫也一樣被擋。
- **SC-D4**：對 `SHARED` 帳本加成員的行為完全不變（含既有的 `USER_NOT_FOUND`、`ALREADY_MEMBER` 規則）。
- **SC-D5**：`SHARED` 帳本的成員退到只剩一位時，`kind` 仍是 `SHARED`，且之後還能再加人。
- **SC-D6**：註冊時自動建立的個人帳本 `kind` 為 `PERSONAL`。
- **SC-D7**：migration 後，既有帳本中成員超過 1 人的為 `SHARED`，其餘為 `PERSONAL`。
- **SC-D8**：`GET /ledgers` 與 `GET /ledgers/{id}` 的回應都含 `kind`。
- **SC-D9**：`pnpm lint / typecheck / test / build` 與 e2e 全綠；migration 進版控且重跑無 pending。

## 4. 資料模型（Prisma）

```prisma
/// 帳本是給自己記的，還是要與別人共用。建立後不可變更。
enum LedgerKind {
  PERSONAL
  SHARED
}

model Ledger {
  // ...既有欄位不動...
  /// 私人帳本不得加入成員；共享帳本即使只剩一位成員，仍然是共享帳本。
  /// 建立後不可變更——轉換會讓「這本帳本誰看得到」在事後改變，而使用者未必察覺。
  kind LedgerKind @default(PERSONAL)
}
```

### 遷移

Prisma 產生的 DDL 只會加欄位並套用預設值。**既有資料的回填要手動加進同一份 migration**：

```sql
UPDATE "Ledger"
SET "kind" = 'SHARED'
WHERE "id" IN (
  SELECT "ledgerId" FROM "LedgerMember" GROUP BY "ledgerId" HAVING COUNT(*) > 1
);
```

這是純加法的遷移，沒有資料流失風險。但**回填只有一次機會**——漏掉的話，既有的共享帳本會被當成私人帳本，從此加不了人，而且看不出原因。

## 5. API 設計

| 方法  | 路徑                    | 變更                                                      |
| ----- | ----------------------- | --------------------------------------------------------- |
| POST  | `/ledgers`              | body 新增選填的 `kind`；預設 `PERSONAL`                   |
| GET   | `/ledgers`              | 回應每筆新增 `kind`                                       |
| GET   | `/ledgers/{id}`         | 回應新增 `kind`                                           |
| PATCH | `/ledgers/{id}`         | 明確接住 `kind` 並回 400 `LEDGER_KIND_IMMUTABLE`          |
| POST  | `/ledgers/{id}/members` | 帳本為 `PERSONAL` 時回 409 `PERSONAL_LEDGER_CANNOT_SHARE` |

`PATCH` 的做法比照 `tracksBalance`：DTO 明確宣告這個欄位，好回一句說得出原因的 400。若不宣告，`forbidNonWhitelisted` 也會擋下來，但訊息只會說「不允許這個屬性」，看的人分不出是自己打錯字還是這個欄位真的不能改。這樣寫也讓規則出現在自動產生的 OpenAPI 文件上。

### 為什麼後端一定要擋（決策 3 的補充）

前端不會給私人帳本畫出「新增成員」的按鈕。但那是**體驗，不是授權**——Swagger UI 就開在 `/docs`，點兩下就能送出請求。規則只能有一個真相來源，而那個來源是後端（`CLAUDE.md` §8，deny by default）。

正常使用的人永遠不會看到這個錯誤。它存在的意義是讓規則在後端成立，以及讓測試能證明它成立。

### 一個順帶的重構

`LedgersService.create(userId, name, tracksBalance)` 加上 `kind` 之後會有四個位置參數，其中兩個是布林與列舉，呼叫端讀起來認不出誰是誰。改為傳入一個具名物件：

```ts
create(userId: string, input: { name: string; tracksBalance?: boolean; kind?: LedgerKind });
```

`createLedgerForUser` 同樣處理。這是純重構，既有測試就是回歸保護網。

## 6. 測試策略

- **Service 單元測試**：私人帳本加成員被擋（含 owner 本人）；共享帳本不受影響；改 `kind` 被擋；建立時的預設值。
- **e2e**：SC-D1～SC-D6 逐條走過。特別是 SC-D5（退到剩一人仍是共享），那是「不可推導」的具體證據。
- **既有測試不改**。`kind` 有預設值，既有的建立呼叫全部仍然合法。若有測試因此變紅，代表這個變更不如預期地相容，要停下來看。
- 遷移的回填沒有自動測試（migration 不進 Jest）。**驗證方式是手動**：遷移前先造一本兩人帳本，遷移後確認它變成 `SHARED`。

## 7. 對前端的影響

本步不動前端，但 2b Slice 2 會用到：

- **Step 3（建立帳本）**：表單多一組單選鈕（私人 / 共享），與「是否連動帳戶」並列。兩者都要標明建立後不可更改。
- **Step 6（成員管理）**：私人帳本不顯示「新增成員」；共享帳本維持現況。
- **Step 4、5（切換器、明細頁）**：可顯示帳本類型，屬純加法。

`LedgerSummary` 與 `LedgerDetail` 都繼承 `Ledger`，所以 `kind` 會自動出現在兩者上，前端不需要額外的型別工作。

## 8. 延後項目

| 項目                   | 說明                                                                                                       | 時機                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------- |
| **複製交易到其他帳本** | 選取多筆交易、指定目標帳本。是「私人想變共享」的唯一解法，也與帳戶延後清單中的「批量修改交易」是同一類工具 | **本步之後儘早排入** |
| **好友清單**           | 加成員改為從好友挑選，而非輸入 email                                                                       | 階段三               |
| **解除封存帳本**       | 見 `phase-2c-accounts.md` §8                                                                               | 待定                 |
| 依 `kind` 篩選帳本清單 | 帳本數量少，前端自己分組即可。觸發條件：單一使用者的帳本超過 20 本                                         | 待定                 |

複製交易需要決定的事不少：目標帳本若不連動，帳戶欄位怎麼處理；分類在目標帳本可能不存在；要不要在兩筆之間留下關聯。這些都該另立 spec，不塞進本步。

## 9. 界線（Always / Ask first / Never）

- **Always**：DTO 驗證；新錯誤碼進 `@ledger/shared`；schema 變更走 migration；規則寫在 service，controller 不做業務判斷。
- **Ask first**：本步的 schema 變更已於 2026-08-23 取得同意。**遷移的回填 SQL 要在套用前給開發者看過**。
- **Never**：讓 `kind` 事後可改；只靠前端隱藏按鈕來實現「私人帳本不能加人」；手動改資料庫。

## 10. Step 拆分概觀（核可後寫入 `tasks/`）

1. **shared 契約**：`LedgerKind`、`Ledger.kind`、`CreateLedgerRequest.kind`、兩個新錯誤碼。
2. **schema + migration**：新 enum 與欄位，含手寫的回填 SQL。
3. **service 與 DTO**：建立時帶 `kind`、`PATCH` 擋下、`addMember` 擋私人帳本；順帶把 `create` 改為具名參數。
4. **測試補完與最終驗收**：對照 SC-D1～SC-D9。
