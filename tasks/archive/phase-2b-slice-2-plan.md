# 實作計畫：階段二 (2b) Slice 2 — 帳本與成員（前端）

> 狀態：**已核可**（2026-08-23；D3 選 A）
> 依據：`docs/specs/phase-2-web-mvp.md` §9 第 5 項。
> 對應成功條件：**SC-7**（帳本列表 / 建立 / 切換 / 明細）、**SC-8**（成員管理）、
> **SC-16**（非連動帳本不顯示帳戶欄位）、**SC-17**（封存）。
> 前置：Slice 1 已合併（PR #23、#24）。**本步不改後端。**

---

## 1. 為什麼是這一塊

目前前端只認得「第一本帳本」。`use-ledgers.ts:17` 寫死了 `query.data?.[0]`，
使用者建不了第二本帳本，也切不過去。家庭模式在畫面上等於不存在。

這一塊同時是後面兩個切片的地基：

- `tracksBalance` 與封存都掛在帳本上。SC-16、SC-17 非得有帳本畫面才驗得了。
- Slice 3 的交易篩選、Slice 4 的分類管理都以「作用中帳本」為範圍。

## 4. 待確認的設計決策

### D1 — 作用中帳本的狀態放哪

「作用中帳本」是首頁記帳時要寫進哪一本的意思。三種做法：

| 方案                        | 做法                                            | 代價                                             |
| --------------------------- | ----------------------------------------------- | ------------------------------------------------ |
| A. context + `localStorage` | 頁首下拉切換，網址不變                          | 帳本狀態看不見，無法用網址分享「某本帳本的畫面」 |
| B. 網址帶帳本：`/l/:id/...` | 每個頁面都帶帳本 id                             | 所有路由都要改，Slice 0、1 的頁面全部受影響      |
| C. A + 明細頁另有自己的網址 | 記帳用 context，`/ledgers/:id` 是獨立的管理頁面 | 兩套定位方式並存，要說清楚各自管什麼             |

**建議 C。** 理由：首頁是「記帳」的入口，換一本帳本不該換網址，那會讓上一頁的
行為變得難以預期。帳本明細是另一件事——它是設定頁，有自己的網址才回訪得了。

一併要處理的細節：`localStorage` 存的 id 可能已經失效（帳本被刪、被移出成員、
被封存）。**必須拿它跟 `/ledgers` 的結果對照**，對不上就退回第一本未封存的帳本。
不做這件事的症狀是首頁一直 404 或空白，而使用者完全看不出原因。

### D2 — 成員管理放明細頁還是彈窗

**建議明細頁（`/ledgers/:ledgerId`）。** 成員是一份會有多列、每列都有操作的清單，
彈窗塞不下。而且明細頁還要放改名、封存、刪除，本來就需要一個頁面。

### D3 — 封存不可逆：**已定案，選 A**（2026-08-23）

**現況查證：後端沒有解除封存的端點。** `LedgersController` 只有
`POST /ledgers/:id/archive`，`PATCH` 只吃 `name`。也就是說，**使用者一旦按下封存，
就再也回不去了**，除非手動改資料庫（本專案禁止）。

**決議：本切片不動後端。** 封存前要求打字輸入帳本名稱，並在彈窗內明說「無法復原」。
SC-17 就此完成。

**理由**：封存的用途本來就是「這本帳收起來」，按錯的機率低。現在插一個後端小步，
會讓這個切片橫跨前後端兩份 spec，節奏會亂。

**解除封存記為延後項目**，寫進 `docs/specs/phase-2c-accounts.md` §8。
重評的觸發條件是「實際用起來後真的封錯過」。實作本身很小：把 `archivedAt` 設回
`null`，加一條 e2e。

### D4 — 刪除帳本必須打字輸入名稱（這不是選擇）

後端契約寫死了：`DELETE /ledgers/:id?confirm=<帳本名稱>`，對不上回 400。
所以 UI 一定要有一個輸入框。

**做法**：給既有的 `ConfirmDialog` 加一個 `confirmText` prop（有值就要求打字相符
才能按確認）。純加法，Slice 1 的三個呼叫點不受影響。

另外要處理 409 `LEDGER_HAS_OTHERS_TRANSACTIONS`——帳本裡有別人記的交易時不准刪。
錯誤訊息要引導去封存，而不是只說「衝突」。

### D5 — 建立帳本時的連動設定怎麼呈現

兩顆 radio，預設「與我的帳戶連動」，下方一行灰字說明**建立後不可更改**。

不用 checkbox，因為這是二選一的兩種帳本，不是「開 / 關」一個功能。用 radio 才有
地方寫兩邊各自適合什麼（一般帳本 vs 出遊分帳、社團公款）。

### D10 — 帳本類型與建立時的參與者（2026-08-23 新增，2d 之後）

2d 讓帳本多了 `kind`（私人 / 共享），建立表單因此變成兩組單選鈕，且**選共享時就地
展開參與者欄位**。表單一頁到底，不做兩步精靈——兩組選擇還撐不起一個「下一步」。

**參與者用輸入 email 的方式**。三個備選都不可行或不該現在做：

- **列出所有註冊使用者**：等於把每個人的 email 公開給每個人。不做。
- **好友清單**：階段三的社交層，現在不存在。
- **邀請連結 / QR**：一次解決「對方沒註冊」與「不知道 email」，是三者中最值得做的，
  但它改變安全模型（拿到連結的人就能加入），需要有效期限、撤銷、角色固定等配套，
  值得自己一份 spec。**另立步驟，不塞進 Slice 2。**

email 輸入不是這些方案的競爭者，而是**永遠存在的底層**：即使好友與邀請連結都做出來，
「我知道他的 email，直接加」仍是一條有效路徑，而且它要求你先在系統外認識這個人——
那正是目前隱私設計的基礎。

**留接縫的方式**：把「清單」與「輸入方式」分開。`LedgerParticipants` 擁有這次要加的
人的清單（增列、刪列、每列的錯誤），`MemberFields` 是一列的 email 與角色。未來加好友
挑選或邀請連結時，動的是「怎麼產生一列」，清單本身不動；Step 6 的新增成員彈窗則直接
重用 `MemberFields`。**不為此加任何抽象層或設定開關。**

**沒有原子性，也不補償刪除**。後端沒有「建立帳本並同時加成員」的端點，前端只能先
`POST /ledgers` 再逐筆 `POST .../members`。某位加不進去（`USER_NOT_FOUND`）時，
**帳本照建，彈窗不關**，就地列出失敗的那幾筆讓使用者改了重試，成功的不重送。

前端不做「補償刪除」——那是在前端實作一致性邏輯，違反單一後端原則。彈窗留著也順帶
解決「Step 5 的明細頁還不存在，失敗的人沒地方補加」這個空窗。

**角色下拉只給 `EDITOR` 與 `VIEWER`**，不給 `OWNER`。owner 能封存、刪除、改成員角色，
在快速填寫的建立表單裡誤選代價太大。要給 owner 請到 Step 6 的成員管理明確變更。

### D6 — SC-16 要動到交易表單

`TransactionForm` 目前無條件顯示帳戶欄位（`TransactionForm.tsx:45`）。
在 `tracksBalance: false` 的帳本，送出會被後端擋成 400 `ACCOUNT_NOT_ALLOWED`。

**做法**：表單改成接收整個 `ledger` 物件（而非只有 `ledgerId`），依 `tracksBalance`
決定要不要渲染帳戶欄位與是否帶 `accountId`。

這是本切片唯一會動到既有已驗收畫面的地方，**要有獨立測試釘住兩種帳本各自的欄位**。

### D7 — 非 owner 看到什麼

SC-8 說「隱藏或擋下並顯示 403」。**建議隱藏**——顯示一顆按下去必定失敗的按鈕沒有意義。

但要在程式註解寫明：**這是體驗，不是授權**。真正的防線在後端的
`@RequireLedgerRole`。前端不做任何權限判斷來決定資料能不能拿，只決定按鈕畫不畫。

例外是「退出帳本」：任何成員都能移除自己，這顆要對所有人顯示。
最後一位 owner 會拿到 409 `LAST_OWNER_CANNOT_LEAVE`，要有對應提示。

### D8 — 封存帳本能不能被設為作用中

**建議不能。** 封存帳本切過去之後，記帳表單的每一次送出都會是 409。
與其做一個註定失敗的表單，不如讓封存帳本只在 `/ledgers` 與明細頁看得到（唯讀）。

切換器只列未封存的帳本。若作用中的帳本剛被封存，自動退回第一本未封存的（同 D1）。

### D9 — 快取失效

現有 query key 都已帶 `ledgerId`（`['transactions', id]`、`['categories', id, type]`），
所以切換帳本會自然重取，**不需要額外處理**。

要補的只有帳本自身的失效：建立 / 改名 / 封存 / 刪除後失效 `['ledgers']`；
成員異動後失效該帳本的 `['members', ledgerId]`。

## 6. 風險與對策

| 風險                                   | 對策                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------- |
| 封存不可逆（D3）                       | 強確認（打字輸入帳本名稱）+ 明說無法復原。解除封存延後，見 D3             |
| `localStorage` 的帳本 id 失效          | 一律與 `/ledgers` 的結果對照後才採用，對不上就退回第一本。獨立測試        |
| 動到交易表單，可能弄壞已驗收的 Slice 0 | 既有 `TransactionForm` 測試是回歸網；新增的兩種帳本測試獨立寫，不改舊測試 |
| 前端隱藏按鈕被誤當成授權               | 註解寫明「這是體驗，不是授權」；不寫任何前端權限判斷去決定資料可不可見    |
| 成員 email 打錯 → `USER_NOT_FOUND`     | 錯誤訊息要說「查無此使用者，對方需要先註冊」，不要只回一句「找不到」      |
| 帳本一多，切換器變長                   | 現階段不處理。觸發條件：超過 10 本要捲動。屆時加搜尋框，元件結構不變      |

## 7. 驗證點

- 每步：`pnpm --filter @ledger/web typecheck` / `test` 綠。
- 全部完成：`pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` 全綠。
- 瀏覽器手動走完：
  1. 建立「出遊分帳」（不連動）→ 切過去 → 記帳表單**沒有帳戶欄位** → 送出成功（SC-16）
  2. 切回個人帳本 → 帳戶欄位回來 → 餘額正確變動
  3. 用第二個帳號加入成員 → 改角色 → 對方看得到帳本
  4. 非 owner 看不到成員管理的操作
  5. 封存 → 帳本從切換器消失 → 開啟「顯示已封存」才看得到（SC-17）
  6. 刪除帳本：confirm 字串不符被擋；有別人的交易時回 409 並引導去封存
