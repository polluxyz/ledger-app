## 1. 為什麼是這一塊

交易是這個系統的核心，但目前前端只做得到「新增」與「看第一頁」。

- 記錯一筆就沒救了——沒有編輯，也沒有刪除。
- `use-transactions.ts:13` 不帶任何查詢參數，永遠只拿後端預設的第一頁 20 筆。
  第 21 筆之後在畫面上等於不存在。
- 表單只有支出與收入。2c 做出來的 `TRANSFER` 在前端完全沒有入口，
  使用者無法表達「從銀行領現金」這件事。

後端這四件事全部做完了（`PATCH`、`DELETE`、`page/limit/from/to/categoryId/type`、
`type: 'TRANSFER'`），這一塊是純前端工作。

## 4. 設計決策（假設清單已於 2026-08-25 確認）

### D1 — 編輯與新增共用同一個表單元件

`TransactionForm` 多收一個選填的 `transaction`：有值就是編輯模式。
新增時內嵌在首頁，編輯時包進既有的 `Dialog`。

**理由**：條件必填規則有四種組合（型別 × `tracksBalance`，見
`packages/shared/src/types/transaction.ts` 的表）。這種規則只該有一份實作。
寫兩個表單一開始比較好寫，但兩邊遲早會分岔，而分岔的症狀是「新增得成、
編輯卻被後端 400」——很難聯想到原因。

### D2 — 編輯別人的交易時，帳戶欄位鎖住（開發者裁示）

後端刻意允許共享帳本裡任何 editor 編輯任何一筆
（`transactions.service.ts:198`）。但別人的帳戶會被遮成 `null`（SC-18），
前端根本拿不到原值。

**做法**：這種情況不渲染帳戶下拉，改成一行說明：
「這筆記在其他成員的帳戶，帳戶無法變更。」送出時不帶 `accountId`，
後端就會沿用原本的帳戶。

**怎麼判斷「這是別人的」**：用 `ledger.tracksBalance && transaction.account === null`。
連動帳本的交易一定有帳戶，而 `account` 只在帳戶不屬於檢視者時才被遮成 `null`
（`transactions.service.ts:432`）。這個條件直接對上「為什麼不能改」，
也省下一次 `/users/me` 請求。

**不用停用的下拉**：停用的欄位會讓人以為是暫時性的問題，事實上它永遠不會開放。

**知會過的替代方案**：完全不給別人的交易編輯入口。開發者選擇保留編輯、只鎖帳戶。

### D3 — 帳戶鎖住時，型別不提供「轉帳」

把別人的支出改成轉帳時，後端只驗證「這次指定的」帳戶屬於誰
（`transactions.service.ts:369`）。轉出沿用他的、轉入填我的——這會被接受，
變成一筆「從他的戶頭轉到我的戶頭」的交易。那不是任何人的本意。

**規則**：帳戶鎖住時只給支出與收入兩顆鈕。

反方向允許：他的轉帳可以改成支出（錢還留在他的帳戶，沒有跨人）。
改完之後「轉帳」那顆鈕就消失、回不去了——這個單向行為在程式註解裡寫明。
它罕見（要在共享帳本裡編輯別人的轉帳），而且錯誤的方向是安全的。

### D4 — 篩選條件放元件 state，不寫進網址

與 Slice 2 的 D1 一致（作用中帳本也不在網址）。

**代價講明**：篩選結果不能用網址分享，重整會回到預設。
**重評的觸發條件**：使用者開始想把「某段期間的某個分類」傳給別人看。

### D5 — 分類篩選要拿「全部型別」的分類

`useCategories(ledgerId, type)` 目前強制帶 `type`——那是為表單設計的
（記一筆支出時只該看到支出分類）。篩選列在「全部型別」時需要全部分類。

後端 `?type=` 本來就是選填（`list-categories-query.dto.ts:8`），
所以把 hook 的參數改成 `type?: CategoryType` 即可，是純加法，
既有兩個呼叫點不受影響。query key 要跟著帶 `type`（可能是 `undefined`）。

選「轉帳」時分類篩選停用並顯示「轉帳沒有分類」——這裡用停用是對的，
因為它會隨著型別切換而恢復，確實是暫時性的。

### D6 — 分頁用「上一頁 / 下一頁」

後端回 `page` / `limit` / `total`，總頁數是 `Math.ceil(total / limit)`。
這是呈現用的除法，不是業務邏輯（SC-13 管的是金額與授權）。

每頁固定 20（後端預設），不做每頁筆數選擇。不做無限捲動——
記帳的人常要「回去看上個月那筆」，頁碼比捲動位置好回訪。

換頁時用 react-query 的 `placeholderData: keepPreviousData`，
畫面保留上一頁的內容直到新的一頁回來，不閃「載入中」。

**篩選條件一改就回到第 1 頁**。少了這件事，使用者會在「第 5 頁」看到空白，
而畫面上沒有任何線索說明原因。

### D7 — 轉帳的表單規則

- 型別鈕變三顆：支出 / 收入 / 轉帳。
- 選轉帳時：隱藏分類欄位，顯示「轉入帳戶」，送出不帶 `categoryId`。
- **非連動帳本（`tracksBalance: false`）完全不出現轉帳鈕**——那本帳本不影響餘額，
  轉帳沒有意義，後端也會擋（400 `ACCOUNT_NOT_ALLOWED`）。
- 帳戶少於 2 個時選轉帳：顯示引導文字並停用送出鈕，比照現有的
  「記帳前要先有一個帳戶」。後端會回 400 `TRANSFER_SAME_ACCOUNT`，
  但讓使用者先撞牆再讀錯誤訊息是不必要的。
- 轉入帳戶的下拉排除已選的轉出帳戶。

### D8 — 清空備註要送空字串

`PATCH` 沒有「清空」的表達方式，`undefined` 代表「不動」
（`update-transaction.dto.ts` 的註解寫明了）。編輯表單把空的備註送成 `''`，
後端才會真的清掉。新增表單維持現況（空的就不送）。

### D9 — 查詢參數進 query key，失效時用前綴

query key 從 `['transactions', ledgerId]` 變成
`['transactions', ledgerId, query]`——不帶參數的話，第 2 頁會覆蓋第 1 頁的快取。

失效時仍用 `['transactions', ledgerId]`。react-query 的失效是前綴比對，
一次涵蓋所有分頁與篩選組合。

**編輯與刪除都必須同時失效 `ACCOUNTS_KEY`。** 餘額是後端依交易算出來的，
改一筆金額、刪一筆帳，餘額就變了。少了這一行不會拋錯、不會讓任何測試變紅，
只會讓餘額停在舊數字——`use-transactions.test.tsx` 已有一條測試釘住「新增」，
這次要為「編輯」與「刪除」各補一條。

### D10 — 刪除用既有 `ConfirmDialog`，不要求打字

刪除帳本要打字是後端 `?confirm=` 契約的要求，不是 UI 選擇。交易沒有這個契約。

確認文字要說明「刪除後無法復原」——後端保留資料列供稽核，
但**沒有還原端點**，對使用者而言就是回不去。

### D11 — e2e 補 6 條（2026-08-25 修訂）

新增情境（編號接續 2e spec §7）：

| #   | 情境                                          | 對應成功條件 |
| --- | --------------------------------------------- | ------------ |
| 7   | 編輯金額 → 帳戶餘額跟著變                     | SC-10        |
| 8   | 刪除 → 該筆從列表消失                         | SC-10        |
| 9   | 轉帳 → 兩個帳戶的餘額都正確變動               | SC-15        |
| 10  | 篩選型別 → 只留下符合的交易                   | SC-10        |
| 11  | 21 筆 → 翻到第 2 頁 → 改篩選回到第 1 頁       | SC-10        |
| 12  | 編輯別人記的交易 → 帳戶鎖住，錢仍記在他的戶頭 | SC-10、SC-18 |

**原本只打算做 7～9**，理由是「篩選與分頁要造 21 筆前置資料，成本不划算」。
實作後開發者反問「Playwright 不能測嗎」，重新評估的結果是那個理由不成立——
迴圈建 21 筆讓整條測試花 0.9 秒。

情境 12 是其中最該做的一條：**帳戶遮蔽是後端做的**，元件測試把它 mock 掉了，
只有 e2e 證得出「別人的帳戶真的被遮起來」與「不帶 `accountId` 時錢仍記在他的
戶頭」。它的斷言直接查對方的帳戶餘額，不只看畫面。

| 風險                                     | 對策                                                                     |
