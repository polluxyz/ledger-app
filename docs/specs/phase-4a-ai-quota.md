## 1. 目標與成功樣貌

4a 每次解析都會呼叫付費模型，目前沒有任何上限。每分鐘限流只擋短時間大量送出，擋不住一整天慢慢用。模型的輸出長度也沒有上限。本步加上 3 道界線：每人每日次數、全站每日次數、每次輸出的 token 上限。另外記下每次呼叫的用量，讓開發者觀測 provider 回報的 token、用量不明的次數與輸入大小。這些紀錄是盡力記錄，不是精確帳單（決策 298 (e)）。

費用估算（GLM-5.3 標價：每百萬 token 輸入 US$1.4、輸出 US$4.4；實測每次輸入約 820～1050 token、輸出 7～95 token）：

- 1 人用滿 50 次：約 US$0.6／日（以每次輸入 2000、輸出 2048 token 估算：50 ×（2000 × 1.4 ＋ 2048 × 4.4）÷ 1,000,000）。
- 全站用滿 500 次：約 US$6／日。
- 這是估算，不是保證的上限。實際金額由供應商計算。有 2 個原因會讓實際金額超過估算：
  - 本期沒有單次完整輸入的硬上限，也沒有總金額的硬上限。清單變長時，單次的費用與延遲跟著上升（決策 298 (i)）。
  - 思考 token 是否算在輸出裡，目前不確定（§5 SC-P27 觀測）。

例子（每人上限 50、全站上限 500，現在是台灣時間 10-24 晚上）：

1. 我今天已經解析 49 次。再送 1 句 → 正常回草稿。這是第 50 次。
2. 再送 1 句 → 畫面顯示「今天的 AI 次數用完了」。模型沒有被呼叫。
3. 我換到另一本帳本再送 → 一樣被擋。額度是所有帳本合計。
4. 我送出一句時模型逾時 → 畫面照舊顯示「AI 暫時沒有回應」。這次算 1 次。
5. 我送出的句子格式錯誤（空白）→ 400。這次不算。
6. 台灣時間過了午夜 → 我又有 50 次。
7. 全站今天已經用了 500 次 → 任何人送出都顯示「AI 暫時沒有回應」，模型沒有被呼叫。

### 範圍外

- **用量畫面、剩餘次數、管理介面**：本期不做。開發者看資料庫與日誌。
- **以 token 或金額計費的額度**：額度只算次數。token 只記錄，不用來擋。
- **清單大小的上限**：只觀測（決策 298）。
- **其他 AI 用途的額度**（理財對話等）：之後的 spec 自己定義（決策 299）。
- **自動清除舊的計數列**。
- **換模型**（10-28 後）：另案處理。換的時候要重驗本步的 SC-P27。

## 3. 資料模型

**新增 2 張表，需要 migration。** 只有數字欄位與 `userId`、日期這 2 個鍵，沒有句子或名稱（決策 298 (i)）。

```prisma
/// 每人每日的 AI 記帳解析用量（4a 額度，決策 294、298）。
/// 同一天第一次呼叫才建列；舊列不自動刪除（決策 299）。
model AiParseDailyUsage {
  userId            String
  /// 台灣時間的日曆日（決策 295）。
  day               DateTime @db.Date
  calls             Int      @default(0)
  promptTokens      BigInt   @default(0)
  completionTokens  BigInt   @default(0)
  /// 還沒拿到合格 usage 的次數：扣額度時加 1，回寫合格 usage 時減 1；這些次數的 token 不在合計裡（決策 298 (b)）。
  usageUnknownCalls Int      @default(0)
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@id([userId, day])
}

/// 全站每日的 AI 用量，當保險絲（決策 292 (b)、299 (b)）。不連使用者。
model AiDailyUsage {
  day               DateTime @id @db.Date
  calls             Int      @default(0)
  promptTokens      BigInt   @default(0)
  completionTokens  BigInt   @default(0)
  usageUnknownCalls Int      @default(0)
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt
}
```

- token 合計用 `BigInt`：單次的 token 數只保證是安全整數，加總可能超過 `Int` 的上限。
- `BigInt` 是有號 64 位元，不是無上限。理論上，單次最大的安全整數乘上全站上限 1000000 仍會超過它。正常的模型用量到不了這個規模，所以不改 schema。真的超過時，回寫失敗，照決策 298 (e) 處理。
- 不加 CHECK 約束擋 `calls` 超過上限：上限是環境變數，會變。

## 5. 成功條件

SC-P18～P26 用假 provider 或 stub 驗證，進 CI；SC-P27 用真的模型，協調者手動跑。

- **SC-P18**（個人上限）：個人上限設 2。
  1. 第 3 次回 429 `AI_DAILY_LIMIT`，provider 只被呼叫 2 次。
  2. 同一人在 2 本帳本各送 → 合計算。重新登入拿新 token 再送 → 仍被擋。
  3. 另一人不受影響。
  4. 關掉 API、重建 app 再送 → 仍被擋（計數在資料庫）。
- **SC-P19**（全站上限）：全站上限設 3，個人上限 10。
  1. A 用 2 次、B 用 1 次 → B 的第 2 次回 503 `AI_UNAVAILABLE`，provider 沒被呼叫。
  2. 被全站擋下的那次，B 的個人次數不變（原子）。
  3. 全站只剩 1 次時，2 人同時送 → 只有 1 人拿到 200，provider 只被呼叫 1 次。
  4. 全站最後 1 次被別人用掉時，今天第一次送出的人不會留下新的個人列。
  5. 個人與全站都用完 → 回 429 `AI_DAILY_LIMIT`，provider 沒被呼叫。
  6. 刪除使用者 → 他的個人列跟著刪除，全站的 `calls` 不變。
- **SC-P20**（併發）：
  1. 新的一天，同一人同時送 5 句，個人上限 2 → 剛好 2 次 200、3 次 429。每人列與全站列都只有 1 列，`calls` 都是 2。
  2. 個人上限 1 → 同時送 3 句，剛好 1 次 200。
  3. 扣額度與回寫 token 交錯併發 → 兩張表的 `calls` 與 token 合計都沒有少算。
- **SC-P21**（算與不算）：
  1. 不算：帳本權限 403、別人的帳本 404、空白句子 400、`AI_NOT_CONFIGURED`、每分鐘限流 429 → 兩張表都沒有變化。
  2. 算：provider HTTP 錯誤、逾時、回非 JSON、被截斷、檢查草稿時的意外例外 → 每種 `calls` 各加 1，`usageUnknownCalls` 照決策 298 (b) 變化，結果分類照 298 (g)。
  3. 同一天換 provider 或 model、重建 app → 次數不歸零。
- **SC-P22**（日期）：用可替換的時鐘。
  1. 台灣時間 23:59:59（UTC 15:59:59）與 00:00:00（UTC 16:00:00）各送 1 次 → 寫在不同的 `day`。
  2. 同一個時間送不同的 `today` → 寫在同一個 `day`。
  3. 23:59:59 扣額度、模型在午夜後才回 → token 記在前一天的列。
- **SC-P23**（0 與設定）：provider 都沒被呼叫，兩張表都沒有新列。
  1. 個人上限 0 → 429。
  2. 全站上限 0 → 503。全站上限 0、個人列已用完 → 仍是 503（不查資料庫）。
  3. 兩個上限都是 0 → 429。
  4. 3 個變數設成 `-1`、`1.5`、`abc`、超出範圍 → `validateEnv` 拋錯。空字串、只有空白 → 用預設值。`0` → 停用。
- **SC-P24**（資料庫失敗）：讓資料庫例外的訊息含 `userId` 與特殊字串。
  1. 扣額度時資料庫拋錯 → provider 沒被呼叫，回 500 `INTERNAL_ERROR`。
  2. 回寫 token 時資料庫拋錯 → 原本是 200 就仍回 200 與草稿，原本是 503 就仍回 503。
  3. 兩種情況的回應與所有日誌通道（Nest `Logger`、`console`）都不出現 `userId` 與特殊字串。
- **SC-P25**（provider 層）：GLM provider 的單元測試。
  1. 請求帶 `max_tokens`，值等於設定。
  2. `finish_reason: "length"` → 被截斷，即使 content 是完整合法的 JSON；usage 照回。`AiService` 回 0 筆草稿、日誌結果是 `truncated`。
  3. 外層合格、content 不是 JSON，但有 usage → 仍回 usage。
  4. token 是負數、小數、字串、缺欄位、`NaN`、`Infinity`、超過安全整數 → 不回 usage。合法的 0／0 照回，和「不回」分得出來。
- **SC-P26**（不記內容）：SC-P11 改成：
  1. 送出含特殊字串的句子後，只有 `AiParseDailyUsage` 與 `AiDailyUsage` 可以改變。這 2 張表只允許新增鍵（`userId`、`day`）、時間欄位與數字。其他資料表不變。
  2. 特殊字串不出現在任何資料表與日誌裡。
  3. 每次扣了額度的呼叫、每次被額度擋下，日誌各有 1 行，欄位照決策 298 (f)，結果分類照 (g)。
- **SC-P27**（真的模型，手動）：`AI_PARSE_MAX_OUTPUT_TOKENS=2048`。舊的綠燈沒有帶 `max_tokens`，不能沿用。
  1. 一句 10 筆消費的句子跑 3 次：每次 10 筆草稿、沒有被截斷、25 秒內回 200。
  2. 新分類 spec 的 SC-P17 五句各跑 3 次，門檻同 SC-P17。包含「高鐵 → 現有的交通」「有『其他』仍提議日用品」「機票不誤選住宿」。
  3. 4a SC-P10 的第 5、6、8 步（昨天、轉帳、看不懂）各跑 3 次，結果和 4a T6 相同。
  4. 記錄每次的輸入與輸出 token、耗時。觀察回應有沒有思考 token 的欄位（例如 `completion_tokens_details.reasoning_tokens`），記下它是否算在 `completion_tokens` 裡。
  5. 確認兩張表的次數與 token 合計和 provider 回報的一致。
  6. z.ai 只用到 10-28；來不及就換模型後跑，並記下用的模型。

## 6. 測試策略

- **隔離與額度測試先寫、先紅**（協調者）：SC-P18、SC-P19 第 2 項、SC-P21 第 1 項。
- 單元：環境變數（SC-P23 第 4 項）、台灣日期換算、GLM provider（SC-P25）、`AiService` 的扣額度順序與資料庫失敗（SC-P24）。
- API e2e（對 PostgreSQL）：SC-P18～P23、SC-P26。併發測試要用真的資料庫，不能用 mock。
- Web 元件測試：W245，以及「其他 429 仍顯示『太頻繁了』」。
- 手動：SC-P27，協調者跑，不放進 CI。
- 既有的 AI e2e 每個測試前清空資料庫，預設上限夠用。額度 e2e 自己覆寫成小的上限。

## 7. 界線

- **Always**：扣額度在呼叫模型之前、同一個資料庫交易裡扣個人與全站；額度日期由伺服器決定；token 不合格就記為用量不明；日誌只記數字與固定分類。
- **Ask first**：改預設的額度數字；加 token 或金額額度；加清單大小上限；加用量畫面；新的 AI 用途共用這兩張表。
- **Never**：在扣額度之前呼叫模型；把資料庫的原始例外交給 filter 寫進日誌；用前端送的日期決定額度；把不明的用量記成 0；日誌或資料表記句子、名稱、模型內容；自動重試模型呼叫；把剩餘次數回給前端。

## 8. 部署

- 有 migration。部署 dev 時在主工作區跑 `prisma migrate deploy`，再 build shared 與 API。請開發者重開 API 與 Vite、按 `Ctrl + Shift + R`。
- 不必改 `apps/api/.env`：3 個變數都有預設值。
- 開發者自己在供應商後台設消費上限（假設 13）。程式不依賴它，也不確定它會不會即時擋下。
- 換模型（10-28 後）時：
  - 重驗 SC-P27。
  - 確認新模型的輸出上限欄位與截斷的回報方式，對應到決策 297 的統一狀態。
  - 照決策 298 (j) 核對 context 長度、單價、觀測到的輸入大小與拒絕方式。
- 多個 API 實例要用相同的 3 個設定（決策 292 (g)）。

## 10. 核可時確認的項目

1. **§3 的 schema 變更**：新增 2 張表，需要 migration。
2. **§4 的 API 變更**：新錯誤碼 429 `AI_DAILY_LIMIT`；OpenAPI 描述修改。Web 要配合（W245）。
3. **決策 292 的 3 個環境變數**與範圍，尤其輸出上限的下限 256。空白視同沒設定、用預設值。
4. **決策 292 (d)、294 (a) 的判斷順序**：個人設定 0 → 429；否則全站設定 0 → 503；兩個上限都大於 0 時，兩邊都不足回個人的 429。
5. **決策 294 (b)**：扣額度時資料庫出錯回 500，不回 503。原始例外不寫進日誌。
6. **決策 298 (e)**：回寫 token 失敗時保留原本的回應（草稿或 503）。用量表因此可能漏記。
7. **決策 296 (b)**：全站上限和 provider 出錯用同一個訊息，使用者分不出來。
8. **決策 298 (b)**：扣額度時先把「用量不明的次數」加 1，拿到合格 usage 再減 1。好處是程序當掉或回寫失敗的呼叫也會算成用量不明，不會像沒花錢。
