## 0. 假設（開發者 2026-10-24 核可）

1. AI 先挑現有分類，意思相近也算。例如「高鐵」可以歸到「交通」，但「機票」不能歸到「住宿」。
2. 「其他」算合適，但只收真的歸納不了的項目。可以歸成一個類別、只是還沒建立的，要提議新分類。
3. 新分類在使用者按 ✓ 時才和交易一起建立。解析時不建立。
4. 寫入用既有的新增交易 API，多一個 `newCategoryName`，和 `categoryId` 擇一。後端在同一個資料庫交易（全部成功或全部取消的一組寫入）裡，先取得或建立分類，再新增交易。
5. 草稿顯示虛線框的「＋分類名」，不加說明文字。點草稿打開表單，可以改選現有分類。
6. 「全部確認」也會建立被提議的分類。每一筆各自成功或失敗。
7. 同帳本、同型別、名稱完全相同，就沿用既有分類。多筆同名只建一個。不做近義合併。
8. 新分類沒有圖示（`icon: null`，畫面顯示通用圖示）。轉帳不提議分類。
9. 帳戶、帳本、對象仍然只能挑現有的。
10. 用真的模型重測。「挑現有分類」與「提議新分類」分開計分（SC-P17）。
11. Jev 不在範圍內。之後另寫評估計畫。

## 1. 目標與成功樣貌

4a 的 AI 對不到分類就留空，使用者要自己去分類頁新增，再回來補。本步讓 AI 直接提議分類名稱，使用者按 ✓ 時一起建立。

例子沿用 4a §1，只在「日常」多一個支出分類「其他」：「日常」的支出分類有「早餐」「午餐」「交通」「其他」。私人帳本「旅行基金」只有支出分類「住宿」與收入分類「薪資」。

1. 我打「高鐵 1490」→ 草稿的分類是「交通」（意思相近，用現有的）。
2. 我打「衛生紙 189」→ 草稿的分類是虛線框的「＋日用品」。衛生紙歸得進「日用品」，只是還沒建立，所以不放進「其他」。
3. 我按這筆的 ✓ → 「日常」多一個支出分類「日用品」，排在最後；明細多一筆衛生紙，分類是「日用品」。
4. 我打「雜支 50」→ 分類是「其他」。
5. 我打「旅行基金 機票 8000 刷卡」→ 帳本是「旅行基金」，分類是「＋交通」。不會選「住宿」。
6. 我打「洗碗精 99、垃圾袋 60」→ 2 筆草稿都是「＋日用品」（第 3 步之後再打，則直接是現有的「日用品」）。按「全部確認」→ 只建 1 個「日用品」，寫入 2 筆交易。
7. 我點一筆「＋日用品」的草稿 → 右側表單的分類預選「＋日用品」。我改選「其他」再按「新增」→ 交易記在「其他」，不建「日用品」。
8. 我打「從儲蓄轉 5000 到現金」→ 轉帳，沒有分類，也沒有提議。

### 範圍外

- **Jev 或其他分類模型**：之後另寫評估 spec（§2.4）。
- **近義合併**：「日用品」和「生活用品」視為不同名稱。
- **改名**：草稿上不能直接改提議的名稱。要別的名字，就到分類頁先建，再改選。
- **手動記帳表單輸入新分類**：表單只在 AI 草稿帶提議時多一個選項。
- **AI 挑圖示**、**AI 新增帳戶／帳本／對象**。
- **使用者同意與隱私政策**：開放給第一位其他使用者前要補（§8）。
- 費用控管與 `max_tokens`（4a 已延後）。

interface TransactionDraft {

interface CreateTransactionRequest {

## 5. 成功條件

用假 provider 驗證 SC-P13～P16；SC-P17 用真的模型。

- **SC-P13**（解析）：測試用的 provider 回決策 283 的 (a)～(e) 五種情況 → 草稿的 `categoryId` 與 `newCategoryName` 照決策 283。另含：提議名稱和現有分類同名 → 變成那個 `categoryId`；51 字 → `null`。
- **SC-P14**（寫入）：
  1. 帶 `newCategoryName` → 建立分類與交易，分類 `icon` 是 `null`、排在同型別最後。
  2. 同帳本同型別已有同名分類 → 沿用，分類數不變。同名但型別不同 → 建新的。
  3. 400：兩個都填、兩個都沒填、轉帳帶 `newCategoryName`、全空白、51 字。
  4. 原子：帶 `newCategoryName`、但帳戶不合法 → 400，而且分類沒有被建立。個人與共享帳本各驗一次。
  5. 併發：同時送 2 個同名請求 → 2 筆交易、1 個分類。
- **SC-P15**（隔離）：對別人的帳本 → 404、檢視者 → 403、封存帳本 → 409。三種情況那本帳本都沒有多出分類。
- **SC-P16**（畫面）：§1 第 2、3、6、7 步照樣運作；「＋」是虛線框、`aria-label` 正確；✓ 可按；寫入後分類頁看得到新分類；第 7 步改選現有分類就不建新分類。
- **SC-P17**（真的模型）：下面 5 句各跑 3 次，共 15 次，每次都在 25 秒內回 200：
  1. 「高鐵 1490」→ `categoryId`＝交通，`newCategoryName: null`。
  2. 「衛生紙 189」（「日常」有「其他」）→ `categoryId: null`，`newCategoryName` 是「日用品」或「生活用品」。
  3. 「雜支 50」→ `categoryId`＝其他。
  4. 「旅行基金 機票 8000 刷卡」→ `ledgerId`＝旅行基金，`categoryId: null`，`newCategoryName`＝交通。
  5. 「早餐 60 現金、午餐 120 刷卡」→ 分類＝早餐、午餐，`newCategoryName` 都是 `null`。
     另外重跑 4a SC-P10 的第 5、6、8 步各 3 次，確認沒有退步。結果填進 plan 的表，失敗也照記。z.ai 只用到 10-28；來不及就換模型後再跑，並在 plan 記下用的模型。

## 7. 界線

- **Always**：新分類只在使用者按 ✓ 或在表單按「新增」時建立；建分類與新增交易同一個資料庫交易；模型的提議逐欄檢查。
- **Ask first**：近義合併；讓 AI 挑圖示；改用 Jev 或其他分類模型；送更多資料給模型。
- **Never**：解析時建立分類；AI 未經使用者確認寫入；新分類跳過新增交易的權限檢查；日誌記使用者的句子或模型的回應。

## 8. 部署、資料與條款

- 沒有 migration。部署時 build shared 與 API，請開發者重開 API 與 Vite、按 `Ctrl + Shift + R`。
- z.ai 只用到 2026-10-28，之後換其他模型。所以這次**不改** `GLM_BASE_URL` 的預設值，留給換模型那次處理。
- **開放給第一位其他使用者之前**要完成，不管用哪家模型：隱私政策；第一次用 AI 前告知並取得同意，列出送給哪家、送什麼、在哪裡處理、保存多久；向模型供應商確認記帳用途沒有違反條款。同意要在資料第一次送到那家供應商之前完成。之後每加一家（例如 Jev），都要重新告知並取得同意。這條寫進 `docs/handoff.md`。
