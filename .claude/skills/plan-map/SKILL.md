# 規劃結構圖

把一份 spec 加一份 plan 的**結構**攤成一頁，讓人看懂：這個切片要做什麼、幾個步驟怎麼串起來、當初為什麼這樣決定、哪些事刻意不做。

## 這頁「不是」什麼

**不是進度看板。** 這是最容易做錯的地方，請嚴格遵守：

- **不要標任何完成狀態**——沒有「未開始 / 進行中 / 已驗收」徽章，不要讀 `- [ ]` / `- [x]` 的勾選狀態。
- **不要放 git 資訊**——分支、最近 commit、未提交變更，全都不要。
- **不要核實程式現況**——不要去比對「這個 Step 的檔案存不存在」。
- **不要算「還剩幾步」、不要指出「卡在哪」、不要建議「下一個動作」。**

開發者要的是**理解架構**，不是被提醒進度。混進狀態資訊會讓頁面立刻過期，也模糊了它真正的用途。

**唯一的例外**：如果**規劃文件自己互相矛盾**（例：spec §9 說 Slice 2、plan D1 說 Slice 1），那要列出來——那是規劃本身的問題，看懂規劃就必須知道。但**程式碼有沒有 bug 不在此列**，那是 code review 的事。

## 精簡優先

**寧可少講，不要講滿。** 每一區只留看懂結構所必需的資訊，細節一律靠代號連結去看原文。

- Step 卡片只寫「做什麼」＋「依據哪個決策」＋「怎麼驗」，各一行。
- 決策只寫一句話結論與立場強度，理由與替代方案留在索引的原文裡。
- 不要把 plan 的段落整段搬過來。

## 頁面結構

1. **這個切片在做什麼**——兩三句，取自 plan §1。
2. **在整個階段裡的位置**——一條 Slice 序列（Slice 0 → 1 → 2 → 3 → 4 → 收尾），每格一行說明，標出目前這一格。**不標完成狀態，只標位置。**
3. **流程與依賴圖**——本頁的核心，用 inline SVG。畫出各 Step 的先後與**為什麼要這個順序**。
4. **Step 一覽**——精簡卡片。
5. **設計決策**——D1、D2… 一句話結論 + 立場強度（必要 / 建議 / 待比較），細節點開看。
6. **成功條件**——哪個 SC 由哪些 Step 達成。
7. **範圍界線**——範圍內 / 範圍外，且**範圍外要寫「那件事在哪裡做」**（例：轉帳 UI → Slice 3）。這一區對理解架構特別重要，不要省略。
8. **規劃內部的矛盾**（若有）——原文並排。
9. **代號索引**——見下節。
10. **頁尾**——生成時間與來源檔案。

### 關於依賴圖

plan 的 §5 通常只規定**順序**，沒有明寫**依賴**。依賴要從 §3（元件規劃）與 §4（決策）推得。

**推出來的依賴一定要在圖旁註明是推論**，例如「Step 4 需要 Step 1 的 `Dialog`，因為 D2 提到帳戶的新增 / 編輯 / 刪除確認要用它三次」。不要把推論畫得像原文明訂的事實。

## 代號連結（本 skill 的核心，必做）

專案裡到處是代號：`D1`～`D6`、`SC-14`、`Step 6`、`SC-C9`。在 Markdown 裡它們只是文字，要查得自己去翻檔案；**在 HTML 裡它們必須是真的能點的連結**。這是這頁存在的主要理由。

1. **頁面上出現的每一個代號都要是連結**，無一例外。內文提到「依據 D5」的那個 `D5`，也要能點。
2. **每個代號有唯一的權威條目**，集中放在頁尾的「代號索引」，內含三樣東西：
   - **Markdown 原文逐字摘錄**（不要改寫、不要摘要——比對的前提是原文）
   - **出處**：檔案路徑 + 行號，如 `tasks/phase-2b-slice-1-plan.md:60`
   - **在 VS Code 開啟**：`vscode://file/<絕對路徑>:<行號>`，點了直接跳到原始檔那一行
3. **點代號的行為是「右側滑出面板就地顯示」，不是跳走**。開發者正在讀某一段，跳到頁尾再捲回來會失去位置。面板內容從索引條目 `clone` 而來，**不要重複寫兩份**。
4. **JS 失效時要能退化**：代號連結本身就是 `href="#ref-D5"` 的錨點，面板只是攔截後的加強。索引區永遠是真實存在的 DOM，不是藏在 JS 字串裡。
5. 抓行號用 `grep -n`，**不要憑印象寫**。行號錯了比沒有連結更糟——它會把人送到錯的地方，而且看起來很篤定。
6. 產出後**驗證沒有斷掉的連結**：比對所有 `href="#ref-…"` 與所有 `id="ref-…"`，兩邊要對得起來。

## 資料來源

| 檔案                    | 取什麼                                                                           |
| ----------------------- | -------------------------------------------------------------------------------- |
| `docs/specs/phase-*.md` | `§1 範圍內 / 範圍外`、`§3 成功條件` 全文、`§9 Step 拆分`與技術債                 |
| `tasks/*-plan.md`       | `§1 為什麼是這一塊`、`§2 範圍`、`§3 元件與相依`、`§4 決策`、`§5 順序`、`§6 風險` |
| `CLAUDE.md` §4          | 這個階段在六個階段中的位置                                                       |

**不要讀 git，不要讀 `apps/` 底下的程式碼。** 這頁談的是規劃，不是現況。

## 範圍

**預設只做當前這一塊**（一個 Slice 或一個後端小步）。開發者若明確指定「整個階段二」或「全專案地圖」才擴大——那時 Step 一覽要再精簡，改以 Slice 為單位。

## 技術要求

- 輸出到 `docs/artifacts/plan-<scope>.html`（如 `plan-slice-1.html`）。同一範圍**沿用同一檔名覆蓋**。
- Self-contained：CSS / JS / SVG 全部 inline，不 `fetch`、不引 CDN。開發者直接用瀏覽器開 `file://`。
- 沿用 `apps/web/src/styles/global.css` 的設計 token（見 `docs/artifacts/design-system.html`）。不要另創配色。
- 互動限於**呈現**：代號面板、摺疊展開、錨點跳轉。不要放勾選框或編輯欄位。
- 寬表格與 SVG 要能在窄視窗縮放或橫向捲動，頁面本身不可橫向捲動。
- 絕不帶入 `.env` / `.env.test` 的任何內容。

## 產出後

在對話中同時給出**這個切片的一句話結構摘要**（幾個 Step、依賴主軸是什麼、有幾個決策待拍板），以及**規劃內部若有矛盾就直說**。不要只回一句「圖做好了」。
