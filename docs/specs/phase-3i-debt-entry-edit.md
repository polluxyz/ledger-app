## 1. 目標與成功樣貌

3h 之後每一筆借還都綁帳戶。選錯帳戶、想補名稱或分類，現在只能撤銷再重記，連動的對象還要重新確認一次。本步讓借還紀錄像一般交易一樣，能直接改名稱、帳戶、分類。

用 3h 的測試資料（我＝test，帳戶「現金」「銀行」）：

1. 房東那筆收回（還款 93、少收 3，現金）：在交易頁點開，表單有金額、日期、分類、帳戶、名稱、備註。把帳戶改成「銀行」→ 還款與少收分支一起搬到銀行，現金 −90、銀行 +90，房東往來餘額不變。
2. 借出給明哥 500：分類選支出分類「居住」，名稱填「押金」。明細第一行仍是「借出 · 明哥」，第二行「押金」，圖示換成「居住」的圖示。餘額不變，這筆不算支出。
3. 收回選收入分類；選到支出分類 → 400。
4. 記新的借還時，表單也能填名稱與分類（選填），欄位順序跟記支出、收入一樣；不再問「記在哪本帳本」，直接記在目前選的帳本。
5. 已連動的對象：只改名稱、帳戶、分類時立刻生效，對方那邊不出現待確認；同時改了金額，金額照舊送對方確認。
6. 交易明細上，房東那筆只顯示一行「收回 · 房東 還清 +$90」。點右邊的 › 展開，下面才出現「欠款 +$93」與「少收 −$3」兩行細項。

### 範圍外

- 改帳本、改種類（借出↔借入）、改對象：照舊撤銷重記。
- 代墊、分帳產生的紀錄：照舊從分帳面板改。
- 分支、呆帳、債務免除：不能單獨改（3h 決策 172、175）。
- 接受對方的連動提議時填名稱與分類：先不做，接受後再改。
- 借還頁的列上顯示名稱與分類：先不做，借還頁看的是欠款。

## 3. 資料模型

**不改 schema。** `Transaction` 本來就有 `title`、`categoryId`、`accountId`。改的是規則：借還交易的分類從「一律不能有」改成「選填、方向要對」。

## 4. API

### 4.1 `PATCH /debt-entries/{id}`

body 多三個選填欄位（只有送出的欄位會變）：

```ts
interface UpdateDebtEntryRequest {
  amount?: Cents;
  date?: string;
  note?: string | null;
  title?: string | null; // 新：null 清除
  accountId?: string; // 新：自己的一般帳戶
  categoryId?: string | null; // 新：null 清除
}
```

- `title`、`accountId`、`categoryId` 改的是這筆紀錄的交易；`accountId` 連分支一起改。
- 錯誤：
  - 種類不能改這些欄位（分帳紀錄、`SETTLEMENT`、`FORGIVE`、`FORGIVEN`）→ 照舊 `409`（`SPLIT_ENTRY_READ_ONLY`／`DEBT_ENTRY_NOT_EDITABLE`）。
  - 舊資料沒有交易（`transactionId` 為 `null`）卻帶這三個欄位 → `409 DEBT_ENTRY_NOT_EDITABLE`。
  - 帳戶、分類的錯誤照決策 177、178。
- 已連動的紀錄：只帶這三個欄位時不呼叫 `proposeAmend`（決策 180）。

### 4.2 `POST /debt-entries`

body 多 `title?: string`、`categoryId?: string`（決策 181）。`categoryId` 不再一律 400，改照決策 178 檢查；方向用後端決定的種類（還款看餘額）。

### 4.3 `DebtEntry` 回應

多一個欄位，給借還頁的修改對話框帶入現在的值：

```ts
recorded: {
  ledgerId: string;
  accountId: string | null; // 呆帳、債務免除為 null
  title: string | null;
  categoryId: string | null;
} | null; // 沒有交易的舊資料為 null
```

只回自己的紀錄（`loadOwnedEntry` 照舊）；`accountId` 是我自己的帳戶，不洩漏別人的資料。

### 4.4 `Transaction` 回應

不變。借還交易有分類時 `category` 照常回傳。

## 5. 成功條件

- **SC-I1**：房東那筆有分支的還款 `PATCH { accountId: 銀行 }` → 還款與分支都在銀行；現金、銀行餘額各變 −90、+90；往來餘額不變；沒有新的提議。
- **SC-I2**：`PATCH { accountId: 我的臨時帳戶 }` → `400 TEMPORARY_ACCOUNT_NOT_SELECTABLE`；`accountId` 是別人的帳戶 → `404`；兩者都沒有寫入。
- **SC-I3**：借出 `PATCH { categoryId: 支出分類 }` → 200，交易 `type` 仍是 `LEND`，帳戶餘額不變；收入分類 → `400 CATEGORY_TYPE_MISMATCH`；別本帳本的分類 → `404`；`categoryId: null` 清掉。收回、借入反過來；還款同借出。
- **SC-I4**：`PATCH { title: '押金' }` → 交易 `title` 是「押金」；`null` 清掉。
- **SC-I5**：連動的紀錄只改名稱、帳戶、分類 → 對方沒有待確認的提議、我的 `sync` 不變；同時改金額 → 照舊送提議。
- **SC-I6**：`POST /debt-entries` 帶 `title`、`categoryId` → 交易帶著；分類方向錯 → 400；以此結清的還款帶分類 → 分類在還款上，分支照舊沒有分類。
- **SC-I7**：`GET /counterparties/{id}/entries` 的每筆有 `recorded`；分帳紀錄也有；沒有交易的舊資料為 `null`。
- **SC-I8**（隔離）：別人的往來紀錄 `PATCH` 任何新欄位 → `404`；用我看不到的帳本的分類 → `404`；回應的 `recorded` 不含別人的帳戶。
- **SC-I9**（畫面）：§1 的 1～6 都做得到。元件測試涵蓋：修改表單 6 個欄位的順序與帶入值、只送有變的欄位、「會送給〇〇確認」只在改金額或日期時出現（W182）、分類清單依方向、新增表單的欄位順序與名稱分類、新增／免除／接受連動都沒有帳本欄位且送出目前帳本的 id（決策 182）、目前帳本是檢視者時沒有這 3 個入口、明細借還列有分類時第一行仍是借還標籤、有分支的還款預設不顯示細項，按 › 才出現 `欠款 +$93` 與 `少收 −$3`（W181）。

## 6. 測試策略

- **單元測試**：分類方向規則（4 種）、修改時分支跟著換帳戶、只改名稱帳戶分類不送提議。
- **API e2e**：SC-I1～I8。隔離測試（SC-I8）由協調者先寫、先看到紅燈。
- **Web**：元件測試涵蓋 SC-I9；Web e2e 一條主線：記收回以此結清（表單沒有帳本欄位）→ 明細只看到實收，展開才看到細項 → 改到另一個帳戶 → 兩個帳戶餘額都對 → 加分類與名稱 → 明細看到名稱。

## 7. 界線

- **Always**：改帳戶時還款與分支在同一個資料庫交易裡改；帳戶一律走 `assertSelectableAccount`；分類方向只在後端檢查一處。
- **Ask first**：改帳本、種類、對象；讓分類影響收支統計。
- **Never**：前端自己決定分類合不合法（只負責列出可選的）；替別人改帳戶；改分支或呆帳的分類。
