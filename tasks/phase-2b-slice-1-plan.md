## 4. 待確認的設計決策

### D1 — `ProtectedRoute` 必須在這一步落地（而非 spec 原訂的 Slice 2）

`/accounts` 是**第一個真正需要登入的頁面**。Slice 0 之所以沒有 `ProtectedRoute`，是因為當時只有一個公開首頁。

一併要處理的安全細節：轉址回來時會把來源頁放在 `location.state.from`，**必須限制為站內相對路徑**。否則構造一個 `from = "https://evil.example"` 的連結，就能在登入後把使用者送到外部網站——典型的開放轉址（open redirect），而且看起來是從我們的網域跳出去的，特別容易取信於人。

做法：只接受以單一 `/` 開頭、且不以 `//` 開頭的字串，其餘一律退回 `/`。

### D2 — 從 `AuthDialog` 抽出通用的 `Dialog`

`AuthDialog` 已經把原生 `<dialog showModal()>` 的用法做對了（焦點鎖定、Esc、遮罩、關閉時卸載）。帳戶的新增 / 編輯 / 刪除確認要再用三次，之後成員管理、帳本建立還會用。

**建議**：把外殼（`<dialog>` + 標題列 + 關閉鈕 + 卸載策略）抽成 `components/Dialog.tsx`，`AuthDialog` 改成它的使用者之一。這是純重構，行為不變，既有的 `AuthDialog.test.tsx` 就是它的回歸保護網。

替代方案是各寫各的——但那會把「關閉時要卸載」這類容易漏掉的細節複製三份，其中一份哪天忘了，症狀是「第二次打開還留著上次的輸入」，很難聯想到原因。

### D3 — 刪除要不要二次確認

後端已經擋掉「有交易引用」的帳戶（409）。所以能刪掉的都是沒用過的帳戶，風險不高。

**建議仍然要確認**，因為刪除是不可逆的，而且會連同初始餘額的設定一起消失。用 `ConfirmDialog`，不做「輸入名稱才能刪」那種強度（那是帳本刪除的等級，這裡不相稱）。

### D4 — 首頁怎麼放餘額

首頁現有三張「本月支出 / 收入 / 結餘」卡片，登入後顯示「即將推出」——它們需要後端彙總端點，這一步不碰。

**建議**：在那三張卡片下方另加一列**帳戶餘額**（每個帳戶一小格：名稱 + 餘額），右側一個「管理」連結到 `/accounts`。

理由是這兩者性質不同：統計卡是「這段期間發生了什麼」，帳戶餘額是「現在還有多少」。混在一起會讓人以為餘額也是本月的數字。

### D5 — 快取失效（最容易漏，且症狀很像 bug）

新增交易會改變帳戶餘額。目前 `useCreateTransaction` 只讓 `['transactions', ledgerId]` 失效——**帳戶餘額不會更新**，畫面上會停在舊數字，直到重整。

要在 `onSuccess` 一併 `invalidateQueries({ queryKey: ['accounts'] })`。

反過來也一樣：調整初始餘額後，餘額變了但交易沒變，只需失效 `['accounts']`。

**這條會寫成獨立測試**——它不會拋錯，只會顯示錯的數字，正是最該被釘住的那種問題。

### Step 1 開工提案的決議

開工前以 HTML 提案頁逐題確認（`docs/artifacts/step-slice-1-01-dialog.html`，不進版控），結論如下。
編號 S1-D1～S1-D5 只屬於 Step 1，與上方 D1～D6 是不同的東西。

| #     | 議題                          | 決議                                                                                                  |
| ----- | ----------------------------- | ----------------------------------------------------------------------------------------------------- |
| S1-D1 | `Dialog` 的 API 形狀          | **單純 props**（`open` / `title` / `onClose` / `children`）。日後要加欄位是純加法，既有呼叫點不受影響 |
| S1-D2 | 「關閉時卸載」由誰負責        | **`Dialog` 內部處理**（`open` 為 false 直接回傳 `null`），呼叫端不必知道有這回事                      |
| S1-D3 | `ConfirmDialog` 何時做        | **Step 4 再做**——現在只能猜它的介面，等真的寫刪除流程時答案自然浮現                                   |
| S1-D4 | 原生 `<dialog>` vs 元件庫     | **維持原生**，不新增相依。S1-D1＋S1-D2 讓日後要換只需改 `Dialog.tsx` 一個檔案，呼叫點不動             |
| S1-D5 | jsdom 的 `showModal` 替身放哪 | **這一步不動**，`Dialog.test.tsx` 自行補上同樣的替身                                                  |

S1-D5 是唯一有衝突的一題：把替身收攏到 `test/setup.ts` 比較乾淨，但那必須從
`AuthDialog.test.tsx` 刪掉 6 行，而本步的核心驗收條件正是「該檔一字未改仍全綠」。
先保住安全網，等重構被證明沒問題後再用獨立 commit 收攏。

### D6 — 負餘額的呈現

`formatAmount` 只加千分位、不加符號，負數會自然變成 `-12,000`。

**建議**：負餘額用紅色（沿用 `TransactionList` 既有的 expense 色），並在帳戶列表明確允許輸入負的初始餘額（`type="number"` 不設 `min`）。信用卡餘額是負的很正常，不該被當成錯誤。

| 風險                                    | 對策                                                                                                                                                           |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 餘額顯示過期（D5）                      | 獨立測試；並在 `use-accounts.ts` 註解寫明「任何會改變交易的操作都要失效這個 key」                                                                              |

| 測試全 mock `fetch`，抓不到真實整合問題 | 已列入收尾的 Playwright 冒煙測試（CORS 與 shared 未重建各咬過一次）                                                                                            |
