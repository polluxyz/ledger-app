## 1. 目標與成功樣貌

2k 首頁的版面是寫死的。資產卡同時裝總額、本月支出分類、帳戶三樣東西，卡片很長。開發者看過 A+ 對照圖後，要把這三樣拆開，並讓每個人可以自己排首頁。

本步分兩件事：

- **A+ 版面**（PR1）：卡片拆成 8 張，按開發者排的桌機預設擺放。卡片的寬度跟著自己所在的容器變，不是跟著整個視窗。
- **可編輯版面**（PR2、PR3）：按「編輯」後，可以拖卡片換位置，拖分隔線改寬度與高度。版面存在伺服器，跟著帳號走。手機網頁維持固定版面。

用一個例子貫穿全篇。使用者在桌機打開首頁，內容區寬 1100px，右側記帳欄關著。

預設版面（12 欄只用來說明比例，實際存的是權重）：

```text
[ 本月支出 4 ] [ 本月收入 4 ] [ 結餘 4 ]
[ 待處理（有資料時才出現，整列） ]
[ 資產趨勢＋總資產 8          ] [ 本月支出 4 ]
[ 最近｜標註 4 ] [ 帳戶 4 ] [ 借還 4 ]
```

### 範圍外

- 隱藏卡片（決策 321）。
- React Native App 的版面與編輯器。資料表留 `surface` 欄位，這次只接受 `WEB`（決策 330）。
- 手機網頁（≤900px）的編輯與它自己的一份版面。
- 新的統計數字、借還排序、首頁專用的彙總端點。
- 卡片內容的設定（例如「本月支出」列幾類）。照 2k，先列 5 類可展開。
- 版面的歷史版本與復原。只有「重設為預設」。

### 已知限制

- 編輯時兩個分頁同時改，只能二選一：載入最新，或用自己的覆蓋。不做合併（決策 329）。
- 版面依卡片的最小寬度換行。換行後的樣子不會存。編輯時畫布不換行，寬度不夠就在畫布裡橫向捲動（決策 324）。
- 草稿只存在這個分頁的記憶體。重新整理或關分頁就沒了，有改動時由瀏覽器原生的提示擋一下（W286）。

## 3. 資料模型

### 3.1 新資料表 `UserHomeLayout`

```prisma
enum HomeLayoutSurface {
  WEB
}

/// 使用者自訂的首頁版面（2l 決策 330）。一個使用者在每種介面一份；沒有列代表用預設版面。
model UserHomeLayout {
  userId        String
  surface       HomeLayoutSurface
  /// 版面 JSON 的格式版本（決策 321、334）。目前只有 1。
  schemaVersion Int
  /// 每次儲存加 1，用來偵測同時編輯（決策 329、333）。
  revision      Int
  /// null 代表重設為預設版面。
  layout        Json?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@id([userId, surface])
}
```

`User` 加一行反向關聯 `homeLayouts UserHomeLayout[]`。

- 主鍵用 `(userId, surface)`，跟 `AiParseDailyUsage` 一樣，不另開 uuid。
- 使用者刪除時一起刪。
- 不存帳本 id、金額、人名。版面只有卡片 id、方向、權重、像素高度。
- migration 只建表與 enum，不動既有資料。

### 3.2 版面格式 v1

型別寫在 `packages/shared/src/types/home-layout.ts`：

```ts
export const HOME_CARD_IDS = [
  'expense',
  'income',
  'net',
  'trend',
  'categories',
  'activity',
  'accounts',
  'debts',
] as const;
export type HomeCardId = (typeof HOME_CARD_IDS)[number];

export type HomeLayoutNode =
  | { type: 'card'; cardId: HomeCardId }
  | { type: 'split'; axis: 'x' | 'y'; children: HomeLayoutNode[]; weights: number[] };

export interface HomeLayoutBand {
  /** 列內的分割樹。 */
  root: HomeLayoutNode;
  /** 使用者額外加的高度（CSS px），0～1600 的整數。 */
  extraHeightPx: number;
}

export interface HomeLayoutV1 {
  bands: HomeLayoutBand[];
}
```

規則：

- `bands` 至少 1 列。
- 每張卡在整份版面剛好出現一次。
- `split` 至少 2 個子節點；`weights` 長度等於子節點數，每個是正整數，加總剛好 10000。
- 不允許同方向的分割直接巢狀（`x` 裡面直接放 `x`）。前端在移動後收合成一層，伺服器拒絕沒收合的版面，讓同一個版面只有一種寫法。
- 預設版面（決策 318）：

```ts
export const DEFAULT_HOME_LAYOUT_V1: HomeLayoutV1 = {
  bands: [
    { root: split('x', ['expense', 'income', 'net'], [3333, 3333, 3334]), extraHeightPx: 0 },
    { root: split('x', ['trend', 'categories'], [6667, 3333]), extraHeightPx: 0 },
    { root: split('x', ['activity', 'accounts', 'debts'], [3333, 3333, 3334]), extraHeightPx: 0 },
  ],
};
```

### 3.3 驗證函式

`packages/shared/src/home-layout.ts` 的 `parseHomeLayoutV1(input: unknown)`，回傳成功（帶收斂後的型別）或失敗原因。後端在 service 呼叫，前端讀回伺服器的版面時也呼叫。

- 先檢查序列化後的 UTF-8 長度 ≤16384 bytes，再走訪。
- 走訪時只看自有屬性。任何物件出現規定以外的鍵就失敗，包括 `__proto__`、`constructor`、`hiddenCardIds`。前端讀回伺服器資料時也靠這條擋。後端的 `__proto__`、`constructor`、`prototype` 在進 service 前已被全站 pipe 刪掉，所以後端靠 PUT 端點的 guard 擋（決策 334）。
- 節點總數（卡＋分割）≤32；分割深度 ≤6；根列數 ≤8。
- 失敗原因只給前端開發用的代碼，不回給使用者看。後端一律回 400 與固定訊息（§4.3）。

## 4. API

### 4.1 `GET /api/users/me/home-layout/web`

回 200：

```json
{ "schemaVersion": 1, "revision": 3, "layout": { "bands": [ … ] } }
```

- 沒存過：`{ "schemaVersion": 1, "revision": 0, "layout": null }`，不建資料列。
- 未登入：401。
- 路徑只接受 `web`，其他值 404（Nest 的路由不比對）。這次不開放 `app`。

### 4.2 `PUT /api/users/me/home-layout/web`

Body：

```json
{ "schemaVersion": 1, "expectedRevision": 3, "layout": { "bands": [ … ] } }
```

- `layout: null` 代表重設。
- body 頂層出現 `userId` 或其他未宣告的鍵：400（全站 `ValidationPipe` 的 `forbidNonWhitelisted`）。
- body 任何一層出現 `__proto__`、`constructor`、`prototype` 自有鍵：400（PUT 端點的 guard，決策 334）。
- `layout` 不用 class-validator 的巢狀驗證，全站 `whitelist` 不會遞迴進去；`layout` 原樣進 service 再交給 `parseHomeLayoutV1`。
- 成功回 200，內容同 GET，`revision` 是新的值。
- 寫入是原子的條件更新：
  1. `expectedRevision` 大於 0：`updateMany where { userId, surface: WEB, revision: expectedRevision }`，把 `revision` 加 1；`expectedRevision` 是 2147483647 時改成設為 1，條件不變，同樣是一次原子更新，不先讀再寫。更新 0 列就回 409。
  2. `expectedRevision` 等於 0：用主鍵 `create`。撞到主鍵（別人先建了）就回 409。
- 409 用新錯誤碼 `HOME_LAYOUT_REVISION_CONFLICT`，回應裡不帶最新版面；前端自己再 GET。

### 4.3 錯誤

| 情況                                                       | 狀態碼 | 回應                                                          |
| ---------------------------------------------------------- | ------ | ------------------------------------------------------------- |
| 版面格式不合格（§3.3 任何一條）、或 guard 擋下的禁用鍵     | 400    | 訊息固定「版面格式不正確」，不帶 `details`                    |
| `schemaVersion` 不是 1、`expectedRevision` 不是 0 以上整數 | 400    | 沿用既有 DTO 驗證錯誤的格式（`Validation failed`＋`details`） |
| 頂層多了未宣告的鍵                                         | 400    | 同上                                                          |
| revision 對不上、或第一次建立時撞到                        | 409    | `HOME_LAYOUT_REVISION_CONFLICT`                               |

版面格式的錯誤不帶是哪一個節點錯，不回傳收到的內容。DTO 層的錯誤照全站既有的 `AllExceptionsFilter` 格式，不另做轉換（advisor 審查）。

### 4.4 流量限制

沿用全站預設（每分鐘 100 次）。拖動中不送請求，只有「完成」送一次，所以不另外收緊。

### 4.5 對前端的影響

- 新端點，既有端點不變。App 目前沒有用到首頁版面。
- OpenAPI 加 `users` 標籤下的兩個端點，DTO 標註完整。
- 前端 query key `['home-layout', 'web']`。不加進 2k 決策 306 的共用失效函式，因為版面和金額無關。

## 5. 成功條件

### PR1（A+ 版面）

- **SC-Y1**（預設版面）：1280px、左側欄展開（內容區 976px，扣掉直向捲軸約 961px）、右側欄關閉，預設版面不換行，8 張卡的位置與寬度比例符合決策 318；左側欄收合時也一樣。待處理卡有資料時在第 1 列下面。
- **SC-Y2**（≤900px）：390px 與 900px 的順序符合決策 323；901px 用桌機版面。沒有「編輯」按鈕。
- **SC-Y3**（換行）：e2e 從卡片登記表的最小寬度與間距算出 3 種內容寬度：剛好放得下、差 1px、全部換行。各寬度的換行結果符合決策 324；沒有橫向捲動；寬度回來後回到原版面。`wrapSplit` 的單元測試另驗權重分配遇到最小寬度時的夾限（例：可用 700px、兩卡最小 320px、權重 6667／3333）。
- **SC-Y4**（總資產）：趨勢卡標題旁的數字等於 `balance-trend` 最後一個月的 `total`；滑過其他月份不變；共享帳本標成「我的總資產」；切帳本時總資產、帳戶清單不重打（2k SC-H2 照樣通過）。趨勢圖面最小 180px，卡片比內容高時圖面跟著變高；點位與最後一點標籤不被裁切。
- **SC-Y5**（金色）：配色「金色」時：第一列是一般分類 → 只有那一列是金色；第一列是未分類或固定分組 → 沒有任何金色；彩色、灰色與 2k 相同。
- **SC-Y6**（百分比）：`2280` bps 顯示 22.80%；`2200` bps 顯示 22%；0 bps 顯示「<0.01%」。統計頁不變。
- **SC-Y7**（借還摘要箭頭）：往來對象（`counterparty.totalBalance`）與未指向帳本的人（`people.amount`）各驗正、負、0：名字只出現一次、「我」那端在、方向依金額正負、0 顯示「兩清」。借還頁、交易頁、分帳、結清的箭頭快照不變。
- **SC-Y8**（容器寬度）：（2026-10-27 修訂，見 2k W264）6 個以上帳戶時，清單的 content box 439px 一欄、440px 兩欄，不管視窗多寬；5 個以下一律一欄。
- **SC-Y9**（2k 不退步）：2k 的 SC-H2～H8、H10～H12、H14、H17 照樣通過。SC-H1 由 SC-Y1、Y2 取代；SC-H9 的箭頭由 SC-Y7 修訂；SC-H13 由 SC-Y4 的趨勢卡高度取代；SC-H15 的版面由 SC-Y25 修訂；SC-H16 由 SC-Y20 補充；SC-H18 由 SC-Y5 修訂。SC-H14 裡首頁交易列的 52px 列高由 SC-Y30 修訂，交易頁的 52px 不變。

### PR2（後端）

- **SC-Y10**（隔離）：
  - A 存的版面，B 用自己的 token GET 拿到的是 `revision: 0, layout: null`。
  - B PUT 不會改到 A 的列。
  - 未登入的 GET、PUT 都是 401。
  - body 帶 `userId` 是 400，資料庫沒有變。
- **SC-Y11**（revision）：
  - 第一次 PUT `expectedRevision: 0` → 200、`revision: 1`。
  - 再用 0 → 409。用 1 → 200、`revision: 2`。
  - `layout: null` → 200、revision 加 1，GET 回 `layout: null`。
  - 回繞（2026-10-28 修訂）：revision 是 2147483646 時存兩次得到 2147483647、1，再存一次得到 2；在 2147483647 用 `layout: null` 重設也得到 1。回繞後再帶 2147483647 → 409，資料不變。資料列不是 2147483647 時帶 2147483647 → 409。兩個請求同時帶 2147483647，剛好 1 個 200、1 個 409，GET 拿到勝出那一個的版面。
  - 兩個請求同時用同一個 revision PUT，剛好 1 個 200、1 個 409；同時用 0 第一次建立也一樣。
- **SC-Y12**（驗證）：`parseHomeLayoutV1` 的單元測試涵蓋 §3.2、§3.3 每一條，每條至少一組合格與一組不合格。API e2e 抽 6 條（超過 16 KiB、重複卡、缺一張卡、`hiddenCardIds`、`__proto__`、`extraHeightPx` 1601）確認是 400，且資料庫沒有變。`__proto__` 與 `constructor` 用原始 JSON 字串送（物件字面值的 `__proto__` 不是自有鍵）。另存一份合法版面再讀回，樹完整、沒有鍵被刪。
- **SC-Y13**（使用者刪除）：刪掉使用者後，他的 `UserHomeLayout` 也不見。

## 7. 界線

- **Always**：使用者只取自 JWT；版面只存卡片 id、方向、權重、高度；伺服器與前端都用同一支驗證函式；寫入用 revision 條件更新；換行結果不存；套件的資料只在轉接層。
- **Ask first**：加 `APP` 或其他 `surface`；版面格式 v2（例如隱藏卡片）；改變卡片數量或 id；加或換套件（含 §6.3 選定之外的版本）；改 CSP。
- **Never**：從 body、路徑或 query 讀使用者 id；版面裡存金額、帳本、人名；把套件的內部 model 存進資料庫；前端在 ≤900px 寫入版面；為了讓套件能動放寬 CSP。

## 10. advisor 的意見與分歧

1. **金色**（雙方一致）：只標第一列的一般分類，第一列是固定分組時整張卡沒有金色。

7. **409 彈窗**（雙方一致）：兩顆按鈕、不加說明段、不做合併。
8. **全文審查的 7 個問題**（advisor 提出，協調者照改）：
   - 全站 `ValidationPipe` 會先刪掉 `__proto__` 等鍵，service 看不到，SC-Y12 原寫法做不到。改成 PUT 端點的 guard（決策 334）。

11. **拖動的最小寬度上限**（第 2 輪，協調者照 advisor 改）：協調者原本在落點檢查加「最小寬度 ≤1152px」，讓新存的版面不換行。advisor 舉反例：8 張卡一列的舊版面最小寬度 2512px，每個移動都會被擋，只剩重設；而且只檢查落點，調高度一樣能繞過。拿掉上限，靠換行與畫布橫向捲動處理（決策 327、SC-Y28）。

14. **首頁窄卡的交易列**（2026-10-25，雙方一致）：`activity` 卡寬 309px 時，卡片內距與 3d 固定的圖示、7rem 金額欄、操作按鈕、間距，只留約 59px 給名稱；借還列再加展開鈕與不縮的「還清」徽章，名稱寬度變 0。advisor 建議合併前修：用 container query 讓窄列換行，保留決策 318 的 4／4／4 與 309px 最小寬度；交易頁不動、不加每列日期、不同時加寬其他卡。驗證要在真的瀏覽器量 309px 的卡，涵蓋各種列。協調者同意（決策 336、SC-Y30）。
