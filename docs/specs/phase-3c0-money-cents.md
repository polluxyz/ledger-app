# Spec：階段三 (3c-0) — 金額單位改成「分」

> 狀態：**已核可**（2026-10-03）
> 依據：3c 代墊與分帳假設確認第 3 版，決策 5 開發者選「乙：存到 0.01 元」（2026-10-02）。理由見 §2 決策 M1。
> 前置：3b-2 修訂 3（#83～#85）已合併。
> 執行順序：**本 spec** → 一個 PR（後端、shared、Web 一起改）→ 3c 代墊與分帳（`phase-3c-split.md`）。

---

## 1. 目標與成功樣貌

讓系統裡的每一個金額都能精確到 0.01 元，分帳的份額不必取整數元。

本步完成後：

1. 資料庫與 API 的金額一律以「分」（0.01 元）為單位的整數存放與傳遞。`333.33` 元存成 `33333`。
2. 既有資料由 migration 換算（×100），帳戶餘額、往來餘額、交易金額在畫面上**完全不變**。
3. 所有金額輸入框接受最多兩位小數；畫面上整數金額照舊顯示 `$3,000`，有零頭才顯示 `$333.33`。
4. 金額仍然**不使用浮點數**（`CLAUDE.md` §6）。前端把輸入字串換成分時用字串運算，不經過 `parseFloat`。

### 範圍內

- Prisma migration：4 個金額欄位 ×100。
- 後端 DTO：金額上下限（決策 M4）；OpenAPI 說明改成「單位：分」。
- `@ledger/shared`：金額型別的文件註解、`Cents` 型別別名、換算工具函式（決策 M5）。
- Web：所有金額的顯示與輸入改走同一組工具函式。
- 單元測試、兩套 e2e 的金額改寫。

### 範圍外

- 多幣別。單位仍只有 TWD。
- 分帳本身（`phase-3c-split.md`）。
- 任何商業規則的改變。這一步只改單位，不改規則。

## 2. 已定案的決策

「來源」欄：**開發者**＝開發者明確表示；**設計**＝本 spec 提出，核可時一併確認。

| #   | 決策                                                                                                                                                                             | 來源   | 理由摘要                                                                                                                                   |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| M1  | **全系統**的金額單位改成分，不是只有分帳改                                                                                                                                       | 開發者 | 整數元的零頭每次都算給付款人，偏差會累積。只讓分帳用分、交易仍用元，同一個數字在不同地方代表不同的錢，加總時會差 100 倍                    |
| M2  | 在 3c 之前**單獨做一步**，一個 PR                                                                                                                                                | 開發者 | 單位改動牽動每一個金額欄位；跟分帳混在同一個 PR，審查時分不出哪個改動是單位、哪個是規則                                                    |
| M3  | **欄位名稱不改**（`amount`、`initialBalance`、`delta`、`balance`…），只改單位。單位寫進 OpenAPI 說明與 shared 型別註解                                                           | 設計   | 後端的規則全部是整數加減，本來就不在乎單位；需要換算的只有 Web 的顯示與輸入。改名會讓 diff 大好幾倍，卻擋不到真正會出錯的地方（見決策 M5） |
| M4  | 單筆金額（交易、往來紀錄、提議）上限 **2,000 萬元**（`2_000_000_000` 分）。帳戶期初餘額範圍 **±2,000 萬元**。資料庫型別維持 `Int`（int4，上限約 2,147 萬元）                     | 設計   | 改成分之後 int4 只剩 2,147 萬元。目前沒有上限，超過時會變成 500 錯誤。改 `BigInt` 會讓 JSON 序列化與前端型別全面改寫，不划算               |
| M5  | 前端**只透過兩個函式**接觸分：`formatMoney(cents)` 顯示、`parseMoneyInput(text)` 輸入（回傳分或 `null`）。放在 `@ledger/shared`，兩者都有單元測試。元件裡不出現 `* 100`、`/ 100` | 設計   | 換算集中在一個地方，漏改的地方用 grep 找得到                                                                                               |
| M6  | 顯示：整數元照舊 `$3,000`；有零頭顯示兩位 `$333.33`、`$0.50`。不做「一律兩位小數」                                                                                               | 設計   | 台幣日常金額幾乎都是整數，一律顯示 `.00` 只是雜訊                                                                                          |
| M7  | 輸入：所有金額欄位改成 `inputMode="decimal"`，最多兩位小數。超過兩位、負號（期初餘額除外）、非數字 → 前端擋下，後端 DTO 也擋（`@IsInt`）                                         | 設計   |                                                                                                                                            |
| M8  | migration 直接換算既有資料（×100），不保留舊欄位                                                                                                                                 | 設計   | 尚未部署到正式環境；開發者的 dev 資料換算後數字不變                                                                                        |

## 3. 受影響的欄位

### 3.1 資料庫（migration ×100）

| 資料表         | 欄位             |
| -------------- | ---------------- |
| `Transaction`  | `amount`         |
| `Account`      | `initialBalance` |
| `DebtEntry`    | `delta`          |
| `DebtProposal` | `amount`         |

`DebtEntry` 的 CHECK 約束只看正負號，換算後仍成立，不必改。

### 3.2 API（只改單位，形狀不變）

| 型別（`@ledger/shared`）      | 欄位                           |
| ----------------------------- | ------------------------------ |
| `Account`、建立／修改帳戶     | `initialBalance`、`balance`    |
| `Transaction`、建立／修改交易 | `amount`                       |
| `Counterparty`                | `balance`、`link.theirBalance` |
| `DebtEntry`                   | `delta`、`balanceAfter`        |
| 建立／修改往來紀錄            | `amount`                       |
| `DebtProposal`                | `amount`、`previous.amount`    |

這是 **API 破壞性變更**（`CLAUDE.md` §14）：同一個數字的意思變了。目前唯一的使用者是本 repo 的 Web，同一個 PR 一起改；行動 App 還沒有。

### 3.3 Web

用到金額的地方（以 2026-10-02 的 `main` 為準）：`AccountBalances`、`AccountList`、`AccountDialog`、`TransactionForm`、`TransactionList`、`HomePage`、`CounterpartyDetail`、`CounterpartyList`、`CounterpartyPicker`、`DebtEntryForm`、`DebtEntryEditDialog`、`PendingCard`。plan 階段用 grep 重新盤點一次。

## 4. 工具函式（`@ledger/shared`）

```ts
/** 金額，單位：分（0.01 元）。只是別名，用來在型別上標出單位。 */
export type Cents = number;

/** 33333 → "$333.33"；300000 → "$3,000"；-120000 → "-$1,200"（負號規則沿用現有 formatMoney）。 */
export function formatMoney(cents: Cents): string;

/** 不帶貨幣符號的版本，給輸入框的預設值用：33333 → "333.33"；300000 → "3000"。 */
export function centsToInput(cents: Cents): string;

/**
 * 使用者輸入 → 分。用字串運算，不經過浮點數。
 * "333.33" → 33333；"3000" → 300000；"0.5" → 50；"1,200" → 120000。
 * 超過兩位小數、空字串、非數字 → null。allowNegative 預設 false。
 */
export function parseMoneyInput(text: string, options?: { allowNegative?: boolean }): Cents | null;
```

`apps/web/src/lib/format.ts` 的 `formatAmount`、`formatMoney` 改成轉呼叫 shared 的版本，或直接移除並改 import（plan 決定）。

## 5. 可驗證的成功條件

- **SC-M1**：migration 之前與之後，對同一份 dev 資料呼叫 `GET /accounts`、`GET /counterparties`、`GET /ledgers/{id}/transactions`，回傳的金額剛好 ×100，畫面上顯示的數字完全相同。
- **SC-M2**：記一筆支出 `333.33`（現金）→ 資料庫存 `33333`；現金餘額少 `$333.33`；交易列表顯示 `−$333.33`。
- **SC-M3**：記一筆支出 `3000` → 列表顯示 `−$3,000`，不是 `−$3,000.00`。
- **SC-M4**：輸入 `1.234`、`abc`、`-5`（支出）→ 前端不能送出；直接打 API 送 `amount: 33333.5` → `400`。
- **SC-M5**：送 `amount: 2_000_000_001` → `400`；`2_000_000_000` → 成功。期初餘額 `-2_000_000_000` 成功、`-2_000_000_001` → `400`。
- **SC-M6**：帳戶期初餘額 2,000 萬元，再收入 2,000 萬元 → 餘額正確顯示 `$40,000,000`（加總超過 int4 也不出錯）。
- **SC-M7**：`parseMoneyInput` 與 `formatMoney` 的單元測試涵蓋 §4 註解裡的每一個例子，以及 `0.1 + 0.2` 類的浮點陷阱（`"0.3"` → `30`）。
- **SC-M8**：還款、以此結清、免除、連動提議的既有 e2e 改用分之後全綠；結清差額可以是零頭（例：欠 `333.33`、還 `333` 並結清 → 結清差額 `−0.33`）。
- **SC-M9**：`grep` 前端元件，除了 shared 的工具函式以外沒有 `* 100`、`/ 100`、`toFixed`。
- **SC-M10**：`pnpm lint / typecheck / test / build / format:check` 與兩套 e2e 全綠；migration 進版控且重跑無 pending。

## 6. 測試策略

- **先寫工具函式的單元測試**（SC-M7），看到紅燈再實作。
- **migration**：在 e2e 資料庫上先灌一組 3b-2 的資料，跑 migration，比對換算前後（SC-M1）。這一步寫成 plan 裡的手動驗證步驟，不進 CI。
- **e2e**：後端的規則不在乎單位，API e2e 的既有金額不必改，只補 SC-M5、SC-M6。Web 的元件測試與 e2e 凡是「用 API 資料斷言畫面金額」的，資料改成分（×100）；從畫面輸入再斷言畫面的不必改。Web e2e 補 SC-M2、SC-M3 的畫面斷言。（2026-10-03 寫 plan 時修正：原文寫成「全部改寫」，但後端測試的金額改不改結果都一樣，改了只是製造 diff。）
- **回歸**：既有的授權與隔離測試只改金額，斷言不變。

## 7. 風險

| 風險                          | 對策                                                                                                                       |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 某個畫面漏改，顯示成 100 倍   | 決策 M5 把換算集中在兩個函式；SC-M9 用 grep 檢查；Web e2e 對每一種金額至少斷言一次                                         |
| Prisma `_sum` 加總超過 int4   | SC-M6 實測。Postgres 的 `SUM(int4)` 回傳 `bigint`，Prisma 轉成 JS number 在安全範圍內；實測不過就改成在 service 裡逐筆加總 |
| 開發者 dev 伺服器跑舊的 build | 合併後替開發者 `prisma migrate deploy` 並重建 shared 與 API，再請開發者重開（`docs/handoff.md`）                           |

## 8. 界線（Always / Ask first / Never）

- **Always**：金額在資料庫、API、後端運算裡一律是整數分；前端換算只走 §4 的函式。
- **Ask first**：把欄位改成 `BigInt` 或 `Decimal`；改任何商業規則。
- **Never**：用浮點數表示或運算金額；在元件裡直接乘除 100。

## 9. Step 拆分

一個 PR。涉及 schema、migration、API 介面，依 `CLAUDE.md` §11 派給 Codex `gpt-6-sol`（xhigh）；協調者先寫 shared 工具函式的型別與單元測試，驗收時逐行看 diff、重跑兩套 e2e。

1. shared：`Cents`、`formatMoney`、`centsToInput`、`parseMoneyInput` 與單元測試。
2. migration（×100）與 DTO 上下限。
3. 後端單元測試與 API e2e 的金額改寫。
4. Web 的顯示與輸入改走 shared 函式；Web e2e 改寫。
