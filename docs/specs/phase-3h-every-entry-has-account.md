# Spec：階段三 (3h) — 每一筆帳都要對到帳戶

> 狀態：**草稿，待核可**
> 依據：開發者 2026-10-14 提出「只要有金額流動，就一定有某個帳戶增加或減少」，並確認假設清單（不記入帳本拿掉、不計入餘額的帳本拿掉、差額改成還款底下的分支、臨時帳戶、預設帶入跟著帳號走、測試資料重建）。
> 前置：3g（#115）已合併並部署到 dev。
> 改寫的既有決策：2c 的 `tracksBalance`（SC-C12 等）、3b 決策 38、3e 決策 123～126、3g 決策 156～158 的資料形式（行為保留）。
> 執行順序：本 spec → plan 與 todo → 實作 PR。

## 1. 目標與成功樣貌

現在有三條路可以記帳卻不動帳戶：借還選「不記入帳本」、記到「不計入餘額」的帳本、共享帳本裡別人付的錢「帳戶待補」。這些帳不在任何帳戶裡，總資產看不出來，久了容易忘。以此結清的差額也不產生交易，收支表上看不到少收或多收的錢。

本步之後的原則：**每一筆帳都要對到一個地方，要嘛是帳戶（真的錢），要嘛是和某人之間的欠款。** 不能有兩邊都沒對到的帳。

用下面的資料貫穿全篇（我＝test，帳戶「現金」）：

| 對象 | 紀錄                                                    |
| ---- | ------------------------------------------------------- |
| 房東 | 3/2 借出 93（現金）、3/6 房東還 90 並以此結清（現金）   |
| 阿德 | 3/3 借出 100（現金）、3/7 阿德還 105 並以此結清（現金） |

花蓮三日（共享帳本）：小華記了一筆「我付的」晚餐 600。

本步完成後：

1. 借出、借入、還款、接受連動，都一定要選帳本和帳戶。表單預設帶入我最近一筆交易用的帳本和帳戶。
2. 建立帳本時不再問「計入餘額」。所有帳本的交易都算進帳戶餘額。
3. 房東那筆還款顯示成：

   ```
   收回 93  還清          現金 +93
     └ −3  少收（支出）    現金 −3
   ```

   現金合計 +90。收支表多一筆 3 元支出。房東的往來餘額 0。

4. 阿德那筆還款顯示成「收回 100 還清」，底下分支「+5 多收（收入）」，現金合計 +105。
5. 小華替我記的 600 進到**我的臨時帳戶**，我的總資產馬上少 600。我把它改到「現金」後，臨時帳戶回到 0。
6. 撤銷房東那筆還款，分支一起撤銷，現金回到 −93，房東的往來餘額回到 93。

### 範圍外（見 §9）

- 「設定預設帳本」：先做「最近一次」，不夠再加。
- 統計頁與分類圖表（還沒有統計頁）。
- 一次還清總額（3f、3g 延後項目，照舊延後）。

## 3. 資料模型

> 依 `CLAUDE.md` §14，schema 變更屬於「先說明再做」。本節核可即視為同意；實作前協調者會再列一次實際的 migration SQL。

### 3.1 schema

```prisma
model Account {
  // …既有欄位不變
  /// 臨時帳戶（3h 決策 167）：每個使用者一個。別人替我記、選不到我的帳戶時先記在這裡。
  isTemporary Boolean @default(false)
}

model Ledger {
  // 刪掉 tracksBalance（3h 決策 165）
}

model Transaction {
  // …既有欄位不變
  /// 這筆是哪一筆還款的結清分支（3h 決策 170）。只有分支有值。
  differenceOfId String?      @unique
  differenceOf   Transaction? @relation("SettlementDifference", fields: [differenceOfId], references: [id], onDelete: Restrict)
  difference     Transaction? @relation("SettlementDifference")
}
```

- 臨時帳戶每人一個：migration 加部分唯一索引 `UNIQUE ("userId") WHERE "isTemporary"`（Prisma schema 寫不出部分索引，用 SQL）。
- 臨時帳戶的名稱存「臨時帳戶」。使用者已有同名帳戶時，migration 把臨時帳戶取名「臨時帳戶 2」，畫面一律顯示「臨時帳戶」。
- 分支一筆還款最多一筆，所以 `@unique`。交易只做軟刪除，`Restrict` 是最後防線。
- `DebtEntry.settlesEntryId` 與 `SETTLEMENT` 種類保留，給 3g 之前與 3g 期間的舊資料讀取；新的「以此結清」不再寫它們。

### 3.2 帳戶餘額

- 餘額照舊是「初始金額＋交易加總」，只是拿掉 `ledger.tracksBalance = true` 的條件。
- 分支照一般收支計算：支出讓帳戶 −，收入讓帳戶 +。

### 3.3 migration 的資料搬移

依序在同一個 migration 裡：

1. 每個使用者建立臨時帳戶。
2. 「不計入餘額」帳本與「帳戶待補」的交易，帳戶填成臨時帳戶：
   - 一般收支：付款人是成員 → 付款人的臨時帳戶；個人帳本沒有付款人 → 記帳人的臨時帳戶。
   - 共享帳本的結清：付錢、收錢的人是成員且帳戶是空的 → 各自的臨時帳戶。
   - 例外（決策 160～162）不動：別人替我付或替我收、非成員付款。
3. 3g 綁定的差額轉成分支：還款紀錄的 `delta` 加上差額的 `delta`，還款交易的金額跟著改；新增一筆分支交易（同帳本、同帳戶，種類依決策 171）；差額紀錄軟刪除。
4. 刪掉 `Ledger.tracksBalance`。

dev 目前的數量（2026-10-14）：不計入餘額的帳本 2 本、要填臨時帳戶的交易 7 筆（含 1 筆結清的付錢那一邊；收錢的是非成員阿美，照決策 161 不動）、維持沒有帳戶的交易 2 筆（1 筆別人替我付、1 筆非成員付款）、3g 綁定的差額 1 筆（房東，會先刪掉）。

### 3.4 測試資料

明哥、房東、阿德是 3g 的測試資料，往來紀錄都沒有帳戶。實作前用 API 撤銷並刪掉這三個對象；實作完成後用綁帳戶的方式重建，並補 §1 的阿德多收情境。

## 4. API

> 依 `CLAUDE.md` §14，API 介面變更屬於「先說明再做」。本節核可即視為同意。

### 4.1 帳本

- `POST /ledgers`、`PATCH /ledgers/{id}`：拿掉 `tracksBalance`。帶了回 `400`（DTO 白名單）。
- `Ledger` 回應拿掉 `tracksBalance`。

### 4.2 交易

- 付款人是我時，`accountId` 一律必填（不再看帳本設定），錯誤碼照舊 `ACCOUNT_REQUIRED`。`ACCOUNT_NOT_ALLOWED` 不再出現。
- 付款人是別的成員：照舊不能帶 `accountId`（`ACCOUNT_NOT_PAYERS`），後端存成他的臨時帳戶。
- 回應的 `accountPending` 意思改成「這筆在我的臨時帳戶」，只對付款人本人為 true。別人的帳戶照舊遮成 `null`。
- `PUT /ledgers/{ledgerId}/transactions/{id}/account`、`PUT /ledgers/{ledgerId}/settlements/{id}/account`：照舊由本人換帳戶，現在是從臨時帳戶換到真正的帳戶。
- 任何端點帶入臨時帳戶的 id 當 `accountId` 或 `toAccountId`：`400 TEMPORARY_ACCOUNT_NOT_SELECTABLE`（新錯誤碼）。
- `Transaction` 回應多兩個欄位：`differenceOfId: string | null`、`difference: { id, type, amount } | null`（還款帶它的分支，給明細畫分支）。
- 對分支呼叫 `PATCH`、`DELETE`：`409 DIFFERENCE_BOUND_TO_REPAYMENT`（新錯誤碼）。

### 4.3 借還

- `POST /debt-entries`：`record` 必須是物件，`null` 回 `400`。
- `POST /debt-proposals/{id}/accept`：會產生交易的提議，`record` 必須是物件。
- 帶 `settle: true` 的還款：`amount` 照舊是實際收付的金額。回應的還款紀錄 `delta` 是還清的欠款，多一個欄位 `difference: { transactionId, type, amount } | null`。
- `PATCH /debt-entries/{id}` 改有分支的還款金額：重算分支（決策 172）。
- `DELETE /debt-entries/{id}` 撤銷有分支的還款：分支一起撤銷。

### 4.4 帳戶

- `Account` 回應多 `isTemporary: boolean`。`GET /accounts` 照舊回全部帳戶（含臨時帳戶），由畫面決定顯示（W174）。
- 對臨時帳戶 `PATCH`、`DELETE`：`409 TEMPORARY_ACCOUNT_LOCKED`（新錯誤碼）。

### 4.5 預設帶入（新）

- `GET /users/me/record-defaults` → `{ ledgerId: string | null, accountId: string | null }`（決策 174）。

### 4.6 錯誤碼（新增）

| 錯誤碼                             | 狀態  | 情況                         |
| ---------------------------------- | ----- | ---------------------------- |
| `TEMPORARY_ACCOUNT_NOT_SELECTABLE` | `400` | 把臨時帳戶當成要記的帳戶     |
| `TEMPORARY_ACCOUNT_LOCKED`         | `409` | 改名或刪除臨時帳戶           |
| `DIFFERENCE_BOUND_TO_REPAYMENT`    | `409` | 單獨修改或撤銷還款底下的分支 |

別人的帳戶、交易、我沒參與過的帳本，一律 `404`（照舊）。

## 5. 成功條件

金額寫成元，API 是分。以 §1 的資料為準。

- **SC-H1**：`POST /debt-entries` 帶 `record: null` → `400`；不帶 `accountId` → `400 ACCOUNT_REQUIRED`。接受連動的新增帶 `record: null` → `400`。
- **SC-H2**：`POST /ledgers` 帶 `tracksBalance` → `400`；`GET /ledgers` 的回應沒有 `tracksBalance`。migration 後，原本不計入餘額的帳本裡的交易都在臨時帳戶，臨時帳戶餘額等於那些交易的合計。
- **SC-H3**：房東還 90 以此結清：還款交易 93（`COLLECT`，現金）、分支 3（`EXPENSE`，現金，`differenceOfId` 指向還款）。現金合計 −93 + 93 − 3 = −3。房東往來餘額 0，往來紀錄沒有 `SETTLEMENT`。
- **SC-H4**：阿德還 105 以此結清：還款 100、分支 5（`INCOME`）。現金合計 +5。
- **SC-H5**：把房東那筆實收改成 91 → 分支 2；改成 95 → 分支變 `INCOME` 2；改成 93 → 分支撤銷。每次現金合計等於「−93 + 實收」，房東往來餘額都是 0。
- **SC-H6**：撤銷房東那筆還款 → 分支一起撤銷，現金 −93，房東往來餘額 93。直接 `DELETE` 或 `PATCH` 分支 → `409 DIFFERENCE_BOUND_TO_REPAYMENT`。
- **SC-H7**：連動的對象記「以此結清」，我接受後我這邊是還款加分支、方向相反；對方撤銷，我接受後兩筆一起撤銷。
- **SC-H8**：小華在花蓮三日記一筆我付的 600 → 我的臨時帳戶 −600，`accountPending` 對我是 true、對小華是 false。我用 `PUT …/account` 換到現金 → 臨時帳戶 0、現金 −600。結清同理。
- **SC-H9**：臨時帳戶當 `accountId` → `400 TEMPORARY_ACCOUNT_NOT_SELECTABLE`；改名、刪除 → `409 TEMPORARY_ACCOUNT_LOCKED`。每個使用者剛好一個臨時帳戶（含新註冊）。
- **SC-H10**：`GET /users/me/record-defaults` 回我最近一筆用真正帳戶的交易的帳本與帳戶；帳本封存或我退出後，`ledgerId` 是 null、`accountId` 照舊；從沒記過帳 → 兩個都 null。
- **SC-H11**（隔離）：別人的臨時帳戶不能被我用 `PUT …/account` 指定、也看不到它的餘額；`record-defaults` 不會回別人的帳戶或我沒權限的帳本；別人的分支 `404`。
- **SC-H12**（畫面）：§1 的 1～6 都做得到。元件測試涵蓋：借還表單沒有「不記入帳本」且預設帶入、帳本對話框沒有「計入餘額」、分支畫在還款下面且沒有「⋯」、臨時帳戶的顯示與換帳戶、撤銷確認框的試算含分支。
- **SC-H13**：回歸：3b～3g 的 API e2e 與 Web e2e 改成「一律綁帳戶」後全綠；`pnpm lint / typecheck / test / build / format:check` 全綠。

## 6. 測試策略

- **授權先行**：SC-H11 的隔離測試由協調者先寫、先看到紅燈。
- **migration**：在測試資料庫灌一份「不計入餘額帳本＋帳戶待補＋3g 綁定差額」的資料，跑 migration 後比對每個帳戶餘額與每個人的往來餘額，和 migration 前的「應有值」一致。
- **單元測試**：分支的計算（少收、多收、少付、多付、剛好還清）、付款人帳戶規則（自己、成員、非成員）、`record-defaults` 的篩選條件。
- **API e2e**：SC-H1～H10。
- **Web**：元件測試涵蓋 SC-H12；Web e2e 一條主線：記借出 → 以此結清少收 → 明細看到分支 → 撤銷 → 分支一起消失；另一條：別人替我記 → 臨時帳戶 → 換到現金。

---

## 7. 界線

- **Always**：還款與分支在同一個資料庫交易裡寫入、修改、撤銷；臨時帳戶只能由本人換出；付款人的帳戶規則只寫在 `payer-account-rules.ts` 一處。
- **Ask first**：再增加不綁帳戶的例外；讓使用者手動選臨時帳戶；改動 migration 搬移的對應規則。
- **Never**：前端自己算分支或餘額；把一筆分支單獨撤銷；替別人選帳戶。

## 10. 核可時一併確認（來源「設計」的項目）

1. **決策 161**：共享帳本裡非成員付的錢維持沒有帳戶。
2. **決策 162**：免除與 3g 之前的舊差額維持不產生交易。另一個做法是把免除也記成一筆收支（免除別人＝支出、被免除＝收入），讓收支表看得到；但它沒有帳戶，等於多一種例外。
3. **決策 164**：沒有交易的舊借還紀錄保留原樣，不強迫補帳戶。
4. **決策 166**：「不計入餘額」帳本的交易搬到臨時帳戶。
5. **決策 169、W174**：臨時帳戶不能手動選、不能改名刪除；帳戶頁只在有餘額或有交易時顯示。
6. **W176**：撤銷確認框的試算含分支。
7. **W177**：帳本已固定的表單只預設帳戶。
