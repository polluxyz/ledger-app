## 1. 目標與成功樣貌

讓兩個都有帳號的人，把各自記的「我跟這個人之間」接起來：**一方記一筆，對方確認後，他那本也自動記一筆方向相反的紀錄**。

本步完成後，使用者可以：

1. 從往來帳裡的某個人（例如「小明」）發出「邀請連動」：輸入對方的 email，或產生一條邀請連結傳給對方。
2. 對方接受時，選自己那邊要接到哪個人（既有的名字，或新建一個）。之後兩本往來帳就連動了。
3. 連動後記借出、借入、還款、免除，對方會收到一個「待確認」。對方接受時選自己的帳本與帳戶，他那邊就記一筆方向相反的紀錄。
4. 改或刪已經同步的紀錄前，畫面先警告；確定後照改，並送一個變更給對方確認。對方不接受也沒關係。
5. 在總覽看到「待確認」：收到的連動邀請與收到的紀錄。
6. 在某個人的往來帳看到對方帳上的餘額，自行核對。
7. 任一方可以解除連動，解除後各自的紀錄都保留，變回單邊記錄。

同時完成兩個延後項目（`phase-3b-debts.md` §9）：

- 選人的欄位改成自訂下拉選單，並能不記帳就先新增一個人（`POST /counterparties`）。
- 改或刪已連動的紀錄前先警告（決策 48 的後半）。

### 範圍外

- 連動前的舊紀錄同步、期初餘額（決策 55）。
- 代墊與多人分帳、「對方幫我付」的同步（決策 62）。
- 推播、email 通知。待確認只在畫面裡顯示。
- 共享帳本的其他成員看到往來（決策 13 不變）。

## 3. 概念與規則

### 3.1 名詞

| 名詞     | 意思                                                                        |
| -------- | --------------------------------------------------------------------------- |
| 連動     | 兩個使用者各自的一個人（`Counterparty`）接在一起。存在 `CounterpartyLink`   |
| 連動邀請 | 帶著 `counterpartyId` 的好友邀請或邀請連結                                  |
| 提議     | 連動後一方記、改、刪一筆紀錄時，送給對方確認的請求（`DebtProposal`）        |
| 配對     | 對方接受「新增」提議後，雙方各一筆紀錄互相指向（`DebtEntry.pairedEntryId`） |
| 發起者   | 送出提議的一方                                                              |
| 接受者   | 收到提議的一方                                                              |

### 3.2 種類對照（接受「新增」提議時）

| 發起者存的種類 | 接受者寫入的種類     | 接受者的 `delta`                                     | 需要 `record` |
| -------------- | -------------------- | ---------------------------------------------------- | ------------- |
| `LEND`         | `BORROW`             | −金額                                                | 是（可 null） |
| `BORROW`       | `LEND`               | ＋金額                                               | 是（可 null） |
| `COLLECT`      | `REPAY`              | ＋金額（檢查見決策 65）                              | 是（可 null） |
| `REPAY`        | `COLLECT`            | −金額（檢查見決策 65）                               | 是（可 null） |
| `FORGIVE`      | `FORGIVEN`（新種類） | ＋（接受者欠的全部）；接受者沒有欠款時不寫、照樣接受 | 否            |

- 還款帶了以此結清：提議記 `settle: true`，接受者那邊照 `phase-3b-debts.md` §3.3，用**自己的餘額**補結清差額。結清差額不配對。
- `FORGIVEN`：被免除，只在接受者欠對方時寫入，讓餘額歸零，不產生交易。`delta > 0`，可以刪除、不能改金額（同決策 40）。
- 發起者那筆與接受者寫入的那筆互相配對。`FORGIVE` 與 `FORGIVEN` 也配對。

### 3.3 提議的狀態

```
         接受（接受者）
PENDING ─┬──────────────▶ ACCEPTED
         │ 拒絕（接受者）
         ├──────────────▶ DECLINED
         │ 系統：被新的變更取代（決策 68）、發起者刪掉還沒被接受的紀錄、解除連動
         └──────────────▶ CANCELLED
```

| 提議種類 | 何時送出                               | 接受時接受者那邊                             |
| -------- | -------------------------------------- | -------------------------------------------- |
| `CREATE` | 連動後新增一筆（決策 62）              | 寫一筆配對紀錄（§3.2），可能產生交易         |
| `AMEND`  | 改了已配對紀錄的金額或日期             | 配對紀錄的金額、日期改成提議的值，交易一起改 |
| `DELETE` | 刪了已配對的紀錄（配對在刪除時就清空） | 刪除原本配對的那筆，交易一起軟刪除           |

- 已結束的狀態不能再轉換，回 `409 PROPOSAL_NOT_PENDING`。
- 接受 `AMEND`、`DELETE` 時，若接受者那筆已經被他自己刪掉，提議直接標成 `ACCEPTED`、什麼都不改。
- 改調整紀錄（`SETTLEMENT`、`FORGIVE`、`FORGIVEN`）的金額本來就不允許（決策 40），所以它們只會有 `DELETE` 提議。

### 3.4 每筆紀錄的同步狀態（給畫面用）

| `sync`     | 條件                                       | 畫面           |
| ---------- | ------------------------------------------ | -------------- |
| `NONE`     | 對象沒連動，或連動前記的，或不送提議的種類 | 不顯示         |
| `PENDING`  | 有一筆自己送出、待確認的提議               | 「等對方確認」 |
| `SYNCED`   | 已配對，且沒有待確認的提議                 | 「已同步」     |
| `DECLINED` | 最近一次送出的提議被拒絕                   | 「對方未接受」 |

`sync` 由後端算出。已配對的紀錄另外回 `paired: true`，畫面用它決定改或刪前要不要警告。

### 3.5 誰能做什麼

| 角色             | 能做                                                                               | 不能做                                                    |
| ---------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 對象的擁有者     | 3b-1 的全部；邀請連動、解除連動；看 `link.theirBalance`                            | 刪除連動中的對象（`409`）                                 |
| 連動的對方       | 只透過自己的對象看到 `theirBalance` 與提議                                         | 讀取對方的對象、往來紀錄、備註、帳本、帳戶、交易（`404`） |
| 提議的接受者     | 看到發起者顯示名稱、提議種類、換成自己角度的種類、金額、日期、是否結清；接受、拒絕 | 看到發起者的備註、帳本、帳戶                              |
| 提議的發起者     | 看自己送出的提議                                                                   | 接受或拒絕自己的提議（`403`）                             |
| 連動邀請的收件者 | 看到發起者顯示名稱；接受時選自己的對象                                             | 看到發起者那邊的對象名字（「小明」是發起者自己取的）      |
| 其他任何人       | 無                                                                                 | 讀取或操作任何連動、提議（`404`）                         |
| 帳本成員         | 看到記在該帳本的借還交易（決策 13）                                                | 從交易追到背後的往來或連動                                |

另外兩條原有規則照樣適用：接受提議時把交易記進某帳本要有 EDITOR 以上且帳本未封存；帳戶必須屬於接受者本人。

## 4. 資料模型（Prisma）

> 依 `CLAUDE.md` §14，schema 變更屬於「先說明再做」。本節核可即視為同意。

```prisma
enum DebtEntryKind {
  // …既有 7 種
  FORGIVEN   // 新增：被對方免除，delta > 0，不產生交易
}

enum DebtProposalType   { CREATE AMEND DELETE }
enum DebtProposalStatus { PENDING ACCEPTED DECLINED CANCELLED }

/// 兩個使用者各一個對象接在一起。一對使用者一筆（low/high 同 Friendship 的排序）。
model CounterpartyLink {
  id                 String   @id @default(uuid())
  userLowId          String
  userHighId         String
  counterpartyLowId  String   @unique
  counterpartyHighId String   @unique
  createdAt          DateTime @default(now())

  // 關聯與 onDelete: Cascade 省略
  @@unique([userLowId, userHighId])
}

/// 連動後送給對方確認的變更。
model DebtProposal {
  id            String             @id @default(uuid())
  fromUserId    String
  toUserId      String
  type          DebtProposalType
  /// 發起者那筆。DELETE 時是已刪除的那筆（軟刪除，仍在）。
  sourceEntryId String
  /// AMEND、DELETE：接受者那筆（送出時的配對對象）。CREATE 為 null。
  targetEntryId String?
  /// 發起者那筆的種類（發起者的角度）。
  entryKind     DebtEntryKind
  amount        Int                // 正整數；DELETE 存刪除當下的值
  date          DateTime
  settle        Boolean            @default(false)
  status        DebtProposalStatus @default(PENDING)
  respondedAt   DateTime?
  createdAt     DateTime           @default(now())
  updatedAt     DateTime           @updatedAt

  @@index([toUserId, status])
  @@index([sourceEntryId, status])
}

model DebtEntry {
  // …既有欄位
  /// 對方那邊配對的紀錄。雙向各存一次，同一個資料庫交易裡寫入與清空。
  pairedEntryId String? @unique
}

model FriendRequest    { /* …既有 */ counterpartyId String? }  // 連動邀請；onDelete: SetNull 不適用，見 §4.1
model FriendInviteLink { /* …既有 */ counterpartyId String? }
```

### 4.1 migration 手寫的部分

1. `DebtEntry` 的 CHECK 加上 `FORGIVEN`：`delta > 0`、`"transactionId" IS NULL`。
2. `DebtProposal` 的部分唯一索引：同一個 `sourceEntryId` 最多一筆 `PENDING`（決策 68）。
3. `CounterpartyLink` 的 CHECK：`"userLowId" < "userHighId"`。
4. `FriendRequest.counterpartyId`、`FriendInviteLink.counterpartyId` 的外鍵用 `ON DELETE CASCADE`：對象被刪，邀請跟著消失（有邀請中的對象照樣可以刪，因為它還沒連動）。

### 5.2 接受連動邀請（既有端點的增修）

| 方法與路徑                          | 改動                                                                                 |
| ----------------------------------- | ------------------------------------------------------------------------------------ |
| `GET /friend-requests`              | 每筆多 `forLink: boolean`；送出的連動邀請另帶 `counterpartyId`（F25，收到的為 null） |
| `POST /friend-requests/{id}/accept` | 連動邀請時 body **必填** `{ counterparty: { id } \| { name } }`；一般好友邀請不可帶  |
| `POST /friend-invite-links/preview` | 回應多 `forLink: boolean`                                                            |
| `POST /friend-invite-links/accept`  | 連動邀請時 body 必填 `counterparty`，同上                                            |

- 已經是好友、還沒連動：連動邀請照常送出，接受時只建立連動。
- `counterparty: { id }` 指到已連動的對象 → `409 COUNTERPARTY_LINKED`；`{ name }` 撞名 → `409 COUNTERPARTY_NAME_TAKEN`。都不消耗邀請。
- 接受時發起者的對象已經連到別人（期間發起者用別的方式連了）→ `409 ALREADY_LINKED`，邀請維持原狀。

### 5.3 提議

| 方法與路徑                          | 說明                                                                                                |
| ----------------------------------- | --------------------------------------------------------------------------------------------------- |
| `GET /debt-proposals`               | `?direction=incoming\|outgoing&status=&page=&limit=`，新到舊                                        |
| `POST /debt-proposals/{id}/accept`  | `CREATE` 且種類需要交易時 body `{ record: {...} \| null }`（規則同 `POST /debt-entries`）；其他不帶 |
| `POST /debt-proposals/{id}/decline` | 拒絕                                                                                                |

```ts
// DebtProposal（一律從呼叫者的角度）
{
  id, type, status,
  direction: 'incoming' | 'outgoing',
  otherUser: { id, name },           // 收到的是發起者，送出的是接受者
  counterpartyId: string | null,     // 我這邊連動的對象；解除後為 null
  entryKind: DebtEntryKind,          // 收到的換成我的角度（§3.2）
  amount: number,                    // CREATE、AMEND 是提議的值；DELETE 是刪除當下那筆的值
  date: string, settle: boolean,
  previous: { amount, date } | null, // F26：收到的 AMEND 才有，取自我自己那筆改之前的值
  createdAt, respondedAt,
}
```

發起者看自己送出的提議時，`entryKind` 是自己的角度、多 `sourceEntryId`。

> 畫面 spec 追加（2026-09-25，`phase-3b2-web.md` §5）：F25 `FriendRequest.counterpartyId`、F26 `DebtProposal.previous`。兩者都只加欄位。

> 實作時的調整（2026-09-25）：加上 `direction`；`fromUser` 改成 `otherUser`，讓同一個型別能表示收到與送出兩種；`DELETE` 也帶金額與日期，讓接受者看得出是哪一筆，所以 `entryKind`、`amount`、`date` 一律有值。見 `tasks/archive/phase-3b2-linking-plan.md` §6。

### 5.4 既有往來紀錄端點的行為改變

- `POST /debt-entries`：對象連動中且種類在決策 62 範圍 → 同一個資料庫交易裡建立 `CREATE` 提議。
- `POST /counterparties/{id}/forgive`：連動中 → 同樣建立 `CREATE` 提議（`entryKind: FORGIVE`）。
- `PATCH /debt-entries/{id}`：已配對且金額或日期有變 → `AMEND` 提議；有待確認的 `CREATE` → 直接更新該提議的金額與日期。
- `DELETE /debt-entries/{id}`：已配對 → 清空雙方配對、建立 `DELETE` 提議；有待確認的 `CREATE` → 提議 `CANCELLED`。
- 回應格式不變；API 介面的變更只有 §5.1～§5.3 列的新增欄位與端點。

### 5.5 錯誤碼

新增：`ALREADY_LINKED`、`COUNTERPARTY_LINKED`、`LINK_INVITE_FROM_THEM`、`PROPOSAL_NOT_PENDING`（皆 409）。
沿用：`NOTHING_TO_REPAY`、`REPAYMENT_EXCEEDS_BALANCE`（接受提議時）、3a 的好友錯誤碼。

### 5.6 同時送達的請求

- 接受提議：先以「`status = PENDING` 才更新」的條件式更新搶下提議，再鎖接受者的對象（決策 50）。兩次接受同時到，只有一次寫入。
- 發起者改紀錄與接受者接受同時發生：兩邊都要鎖發起者那筆紀錄所屬的對象；後到的一方看到提議已不是 `PENDING`，照 §3.3 處理。
- 建立連動：`CounterpartyLink` 的三個唯一值擋下重複，service 把 `P2002` 轉成 `409 ALREADY_LINKED`。

## 6. 可驗證的成功條件

- **SC-K1**：`POST /counterparties { name: ' 小明 ' }` 建立「小明」；再建一次 → `409 COUNTERPARTY_NAME_TAKEN`。`GET /counterparties?q=明` 找得到。
- **SC-K2**：A 從「小明」用 B 的 email 邀請連動；B 接受並選新名字「阿A」→ A、B 成為好友；A 的「小明」與 B 的「阿A」`link` 互相指向對方使用者。連動前的紀錄與餘額不變。
- **SC-K3**：用邀請連結做一次 SC-K2，結果相同；B 選既有未連動的對象也可以；選已連動的對象 → `409 COUNTERPARTY_LINKED`，連結不被消耗。
- **SC-K4**：已連動再邀請 → `409 ALREADY_LINKED`；B 已邀請 A、A 再邀請 B → `409 LINK_INVITE_FROM_THEM`。
- **SC-K5**：連動後 A 記借出 120（現金）→ A 的餘額 +120 立即生效；B 收到 `CREATE` 提議（種類顯示 `BORROW`、金額 120，看不到 A 的備註、帳本、帳戶）。B 接受並選自己的帳本與帳戶 → B 的「阿A」餘額 −120、B 的帳戶 +120；兩筆紀錄配對，雙方 `sync = SYNCED`。
- **SC-K6**：接著 B 記還款 120 → 存成 `REPAY`；A 接受 → A 那筆是 `COLLECT`，雙方餘額 0。
- **SC-K7**：A 記借出 100，B 拒絕 → A 的紀錄保留、`sync = DECLINED`，B 的往來帳沒有變化。
- **SC-K8**：接受者餘額為 0 時接受還款提議 → `409 NOTHING_TO_REPAY`，提議維持 `PENDING`，之後可以拒絕。帶 `settle` 的還款提議，B 的結清差額依 B 自己的餘額計算。
- **SC-K9**：A 免除（A 帳上 B 欠 50，B 帳上欠 A 30）→ B 接受 → B 寫一筆 `FORGIVEN` +30，餘額 0，沒有交易。
- **SC-K10**：A 把已同步的借出 120 改成 150 → B 收到 `AMEND`；接受 → B 那筆與它的交易一起變 150。A 再改成 160 之前 B 沒回應 → 舊提議 `CANCELLED`，只剩一筆 `PENDING`。
- **SC-K11**：A 刪掉已同步的紀錄 → 雙方配對清空、B 收到 `DELETE`；B 拒絕 → B 那筆保留。A 刪掉還在 `PENDING` 的新增 → 提議 `CANCELLED`。
- **SC-K12**：A 解除連動 → 好友關係也解除；雙方的對象仍在且名字不變（A 的「小明」、B 的「阿A」）、紀錄都在、`paired = false`、`link = null`；所有 `PENDING` 提議與連動邀請 `CANCELLED`。`DELETE /friends/{B}` 有同樣效果。對方刪除帳號時同樣只解除連動，我的對象與紀錄不受影響。
- **SC-K13**：刪除連動中的對象 → `409 COUNTERPARTY_LINKED`。
- **SC-K14**：`link.theirBalance`：A 帳上 +120、B 帳上 −100 → A 看到 `theirBalance = 100`，B 看到 `-120`。
- **SC-K15**（隔離）：第三人 C 讀或接受 A 的提議 → `404`；A 接受自己的提議 → `403`；C 讀 A 的對象 → `404`。B 接受提議時指定別人的帳戶 → `404`、VIEWER 帳本 → `403`、封存帳本 → `409`，都不留下任何紀錄。
- **SC-K16**：兩個接受請求同時送達同一個提議 → 只寫入一筆配對紀錄。
- **SC-K17**：連動中記 `PAID_FOR_ME` → 照記，不產生提議。
- **SC-K18**：`pnpm lint / typecheck / test / build / format:check` 與兩套 e2e 全綠；migration 進版控且重跑無 pending。

畫面的成功條件寫在 `phase-3b2-web.md`。

## 10. 界線（Always / Ask first / Never）

- **Always**：接受提議時以接受者自己的餘額檢查；提議與配對的寫入和發起者的紀錄在同一個資料庫交易裡；隔離測試先於實作。
- **Ask first**：放寬 §3.5；讓提議不經接受就寫入對方的帳。
- **Never**：不經對方接受就改他的往來紀錄或交易；把發起者的備註、帳本、帳戶、對象名字給接受者；在前端推導同步狀態或對方餘額。
