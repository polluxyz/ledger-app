## 1. 目標與成功樣貌

讓使用者記「一筆錢裡有別人的份」：我先付（收）了一筆，其中一部分是別人的；或是別人先幫我付（收）了。帳戶照實際收付的錢變動，統計只算自己那份，別人那份變成往來帳裡的誰欠誰。

用一個例子貫穿全篇：**晚餐 3,000 元，我刷國泰世華付，我、小明、小華、阿美 4 人均分**。

- 國泰世華 −3,000；我的支出 750；小明、小華、阿美各欠我 750。
- 小明、小華已連動，各收到一個待確認；接受後他們那邊各記一筆「對方幫我付」支出 750，帳戶不動。
- 交易列表一列「晚餐 −$3,000」標「分帳」，往下展開看到每個人的份。

本步完成後，使用者可以：

1. 在記帳表單的支出或收入，把帳戶切成「別人先付（代收）」，只記自己那份與欠誰。
2. 打開分帳，選要分的人，用均分、自訂金額或自訂比例分。
3. 修改或刪除一筆分帳，包括增減人、改付款人；一般交易與分帳可以互轉。
4. 在交易列表看到合併成一列的分帳，展開看明細。
5. 已連動的人收到待確認，接受後他那邊自動記一筆。

### 範圍內

- 交易新增「名稱」欄位（所有手動交易）。
- 分帳物件、3 種新的往來種類、分帳端點、交易列表合併。
- 連動的鏡像對照（4 種）與提議帶名稱。
- `@ledger/shared` 型別、錯誤碼、份額計算的純函式。
- 單元測試與 e2e。Web 畫面見 `phase-3c-web.md`（本檔 §7 先記已定案的方向）。

### 範圍外（見 §9）

- 多人一起付款（我付 2,000、小明付 1,000）。
- 共享帳本裡「成員之間誰欠誰」的畫面與結清（決策 87）。
- 雙方溝通重複帳的訊息功能（決策 89）。
- 多幣別、計算機鍵盤。

## 3. 概念與規則

### 3.1 名詞

| 名詞   | 意思                                                             |
| ------ | ---------------------------------------------------------------- |
| 分帳   | 一筆有別人份的支出或收入（`Split`）。存總額、付款人、分法、名單  |
| 付款人 | 先付（收）這筆錢的人：我，或我的一個對象。收入時畫面叫「收款人」 |
| 名單   | 要分這筆錢的人（`SplitParticipant`），可以包含我                 |
| 份額   | 名單裡每個人分到的金額，單位分，> 0                              |
| 吸收者 | 承接零頭的人（決策 92）                                          |
| 精度   | 其他人份額取整的單位：分（預設）或元（決策 91）                  |
| 我那份 | 名單裡我的份額；我不在名單裡時是 0                               |

### 3.2 4 種往來種類與鏡像

### 3.4 份額計算

純函式 `computeSplitShares`，放在 `@ledger/shared`，後端以它為準，Web 用它預覽。輸入：總額 `T`（分）、分法、名單（含各人的金額或萬分比）、付款人、精度。

1. 檢查名單：至少 1 人、沒有重複、我最多出現一次。
2. **自訂金額**：份額＝使用者給的值。加總 ≠ `T` → `400 SPLIT_SUM_MISMATCH`。
3. **均分**：每人權重 1/n。**自訂比例**：權重＝萬分比 / 10000，加總 ≠ 10000 → `400 SPLIT_SUM_MISMATCH`。
4. 精確值 `e_i = T × 權重`。吸收者以外的人：`s_i = 四捨五入(e_i / u) × u`，`u` 是精度（分＝1、元＝100）。吸收者：`T − Σ 其他人`。
5. 任何人的份額 ≤ 0 → `400 SPLIT_SHARE_NOT_POSITIVE`。

| 例子                                         | 精度 | 結果                                |
| -------------------------------------------- | ---- | ----------------------------------- |
| 1,000 元，我付，3 人均分                     | 分   | 小明 333.33、小華 333.33、我 333.34 |
| 1,000 元，我付，3 人均分                     | 元   | 小明 333、小華 333、我 334          |
| 2,000 元，我付，3 人均分                     | 元   | 小明 667、小華 667、我 666          |
| 3,000 元，小明付，我 20%、小明 40%、小華 40% | 分   | 我 600、小華 1,200、小明 1,200      |
| 0.02 元，3 人均分                            | 分   | `400 SPLIT_SHARE_NOT_POSITIVE`      |

自動調整（決策 94）另一個純函式 `fillRemainingShares`：給已固定的人與值，回傳其他人平分剩下的結果（同樣的取整與吸收規則）。只給畫面用，後端不呼叫。

### 3.5 寫入的組合

`P` 是付款人，`m` 是我那份，`s_i` 是別人 `i` 的份額。

| 類型 | 付款人 | 寫入                                                                                                                |
| ---- | ------ | ------------------------------------------------------------------------------------------------------------------- |
| 支出 | 我     | `m > 0` 時一筆 `EXPENSE m`（帳戶＝所選帳戶）；名單裡每個別人一筆 `PAID_FOR_THEM s_i`＋`LEND s_i` 交易（同一個帳戶） |
| 支出 | 別人   | 一筆 `PAID_FOR_ME m`＋`EXPENSE m` 交易（沒有帳戶），對象＝`P`。名單裡其他人不產生任何紀錄                           |
| 收入 | 我     | `m > 0` 時一筆 `INCOME m`；每個別人一筆 `RECEIVED_FOR_THEM s_i`＋`BORROW s_i` 交易                                  |
| 收入 | 別人   | 一筆 `RECEIVED_FOR_ME m`＋`INCOME m` 交易（沒有帳戶），對象＝`P`                                                    |

- 所有交易的名稱＝分帳的名稱、日期＝分帳的日期、帳本＝分帳的帳本；分類只掛在我那份（支出或收入）上；備註只存在分帳上。
- 全部在同一個資料庫交易裡寫入；任何一步失敗，什麼都不留下。寫往來紀錄前照 3b 決策 50 鎖住每個相關的對象（依 id 排序上鎖，避免死結）。
- 我付的分帳裡，名單必須有我以外的人；否則回 `400 SPLIT_NOT_NEEDED`（那是一般交易）。修改時例外，見決策 105。

### 3.6 誰能做什麼

| 角色         | 能做                                                 | 不能做                                                                     |
| ------------ | ---------------------------------------------------- | -------------------------------------------------------------------------- |
| 分帳的擁有者 | 讀取、建立、修改、刪除自己的分帳                     | —                                                                          |
| 其他任何人   | 無                                                   | 讀取或操作別人的分帳（`404`）                                              |
| 帳本成員     | 看到記在該帳本的每一筆交易（含名稱，同既有規則）     | 看到分帳、名單、份額：交易回應的 `split` 只對擁有者有值，其他成員是 `null` |
| 連動的對方   | 透過提議看到名稱、種類（換成自己的角度）、金額、日期 | 看到分帳的總額、名單、其他人的份額、備註、帳本、帳戶                       |

另外兩條原有規則照樣適用：分帳記進某帳本要有 EDITOR 以上且帳本未封存；帳戶必須屬於呼叫者。名單與付款人的對象必須屬於呼叫者（否則 `404`）。

## 4. 資料模型（Prisma）

> 依 `CLAUDE.md` §14，schema 變更屬於「先說明再做」。本節核可即視為同意；實作前協調者會再列一次實際的 migration SQL。

```prisma
enum DebtEntryKind {
  // …既有 8 種
  PAID_FOR_THEM      // 我幫對方付：delta > 0，交易型別 LEND
  RECEIVED_FOR_THEM  // 我幫對方收：delta < 0，交易型別 BORROW
  RECEIVED_FOR_ME    // 對方幫我收：delta > 0，INCOME、沒有帳戶
}

enum SplitType      { EXPENSE INCOME }
enum SplitMethod    { EQUAL AMOUNT RATIO }
enum SplitPrecision { CENT YUAN }

/// 一筆有別人份的支出或收入（spec 3c）。存整份，個人角度只用到牽涉到我的部分（決策 87）。
model Split {
  id                  String         @id @default(uuid())
  ownerId             String
  ledgerId            String
  type                SplitType
  categoryId          String
  total               Int            // 分，> 0，≤ 2,000 萬元
  date                DateTime
  title               String?        // ≤ 100 字
  note                String?        // ≤ 500 字
  /// 付款人（收入時是收款人）。null＝我。
  payerCounterpartyId String?
  /// 我付且帳本連動時必填；別人付或不連動帳本時為 null。
  accountId           String?
  method              SplitMethod
  precision           SplitPrecision @default(CENT)
  deletedAt           DateTime?
  createdAt           DateTime       @default(now())
  updatedAt           DateTime       @updatedAt

  participants SplitParticipant[]
  transactions Transaction[]
  entries      DebtEntry[]
  // owner、ledger、category、payer、account 的關聯省略；全部 onDelete: Restrict，owner 為 Cascade

  @@index([ownerId, deletedAt])
  @@index([ledgerId])
}

/// 名單裡的一個人。份額由後端算好存下來。
model SplitParticipant {
  id             String  @id @default(uuid())
  splitId        String
  /// null＝我。
  counterpartyId String?
  share          Int     // 分，> 0
  /// 萬分比，只有 RATIO 有值。
  ratio          Int?
  sortOrder      Int

  split        Split         @relation(fields: [splitId], references: [id], onDelete: Cascade)
  counterparty Counterparty? @relation(fields: [counterpartyId], references: [id], onDelete: Restrict)

  @@unique([splitId, counterpartyId])
}

model Transaction {
  // …既有欄位
  title   String?   // ≤ 100 字（決策 84）
  splitId String?   // 分帳產生的交易（含我那份）
  split   Split?    @relation(fields: [splitId], references: [id], onDelete: Restrict)
  @@index([splitId])
}

model DebtEntry {
  // …既有欄位
  splitId String?   // 分帳產生的往來紀錄；接受提議產生的為 null
  split   Split?    @relation(fields: [splitId], references: [id], onDelete: Restrict)
}

model DebtProposal {
  // …既有欄位
  title String?     // 決策 101
}
```

### 4.1 migration 手寫的部分

1. `DebtEntry` 的 CHECK 加上新種類：`PAID_FOR_THEM` → `delta > 0`；`RECEIVED_FOR_THEM` → `delta < 0`；`RECEIVED_FOR_ME` → `delta > 0` 且 `"transactionId" IS NOT NULL`。
2. `Split` 的 CHECK：`total > 0`；`"payerCounterpartyId" IS NULL OR "accountId" IS NULL`；`length(title) <= 100`。
3. `SplitParticipant` 的 CHECK：`share > 0`；`ratio IS NULL OR ratio BETWEEN 0 AND 10000`。另加部分唯一索引：同一個 `splitId` 的 `counterpartyId IS NULL`（我）最多一列——Postgres 的唯一索引把多個 null 視為不同，`@@unique` 擋不住。
4. `Transaction` 的 CHECK：`length(title) <= 100`。

### 4.2 對既有規則的連帶影響

- **對象刪除**：對象出現在任何未刪除分帳的名單或付款人 → `409 COUNTERPARTY_HAS_ENTRIES`（沿用，訊息相同：有紀錄就不能刪）。
- **對象合併**（3b-2 決策 76）：被併的對象在名單與付款人的引用一起搬過去；同一筆分帳因此出現兩次同一人 → 合併兩列、份額相加。
- **帳本真刪**：帳本內有分帳的交易（含已軟刪除）→ `409 LEDGER_HAS_DEBT_TRANSACTIONS`（沿用）。
- **解除連動**：不影響分帳；照 3b-2 決策 71 只拆配對、取消待確認。

### 5.1 分帳

| 方法與路徑            | 說明                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------- |
| `POST /splits`        | 建立。可帶 `fromTransactionId` 把一般交易轉成分帳（決策 105）                                        |

// POST /splits、PATCH /splits/{id} 的 body（PATCH 全部欄位都要帶，整份取代）

}

// Split 回應

  id, type, ledgerId, category: { id, name }, total, date, title, note,

- 別人付時，`participants` 照樣回整份名單（擁有者自己存的），畫面依決策 87 只顯示我與付款人。
- `fromTransactionId`：必須是呼叫者建立的一般 `EXPENSE` 或 `INCOME`、型別與 `type` 相同、不屬於任何分帳或往來 → 否則 `409 TRANSACTION_NOT_CONVERTIBLE`。

### 5.2 交易端點的調整

- `POST` / `PATCH /ledgers/{id}/transactions`：多一個選填的 `title`（≤ 100 字）。
- 交易回應多兩個欄位：`title: string | null`、`split: TransactionSplitRef | null`。
- `PATCH` / `DELETE` 有 `splitId` 的交易 → `409 SPLIT_TRANSACTION_READ_ONLY`（決策 106）。
- `GET /ledgers/{id}/transactions` **合併分帳**：呼叫者是分帳擁有者時，同一個分帳的交易只回一列——有我那份就是那一筆，沒有就是建立最早的一筆——並帶 `split`。分頁的 `total` 以合併後計算。`type`、`categoryId`、日期篩選套用在分帳本身。其他帳本成員照舊看到每一筆、`split` 為 `null`。

```ts
// 交易列表展開所需的資料一次帶齊，不必再打 GET /splits/{id}
interface TransactionSplitRef {
  id: string;
  total: number; // 分；我付時列表顯示這個
  myShare: number; // 分；我不在名單時為 0
  payer: { counterpartyId: string; name: string } | null;
  /** 只有牽涉到我的人（決策 87）：我付時是名單裡的別人；別人付時只有付款人。 */
  counterparts: Array<{
    counterpartyId: string;
    name: string;
    amount: number; // 分
    direction: 'THEY_OWE_ME' | 'I_OWE_THEM';
    sync: 'NONE' | 'PENDING' | 'SYNCED' | 'DECLINED';
  }>;
}
```

### 5.3 往來與提議端點的調整

- `POST /debt-entries`：`kind: 'PAID_FOR_ME'` → `400`（決策 107）。
- `PATCH` / `DELETE /debt-entries/{id}`：有 `splitId` 的紀錄 → `409 SPLIT_ENTRY_READ_ONLY`，要改走分帳端點。
- `GET /counterparties/{id}/entries`：每筆多 `splitId`，畫面可以從往來帳點回分帳。
- `DebtProposal` 回應多 `title: string | null`。
- `POST /debt-proposals/{id}/accept`：鏡像是 `PAID_FOR_ME`、`RECEIVED_FOR_ME` 時，body 必填 `record: { ledgerId }`（不可帶 `accountId`）與 `categoryId`；可帶 `title` 覆寫名稱。鏡像是 `PAID_FOR_THEM`、`RECEIVED_FOR_THEM` 時，規則同借出（`record` 可為 `null`）。

### 5.4 錯誤碼

新增：`SPLIT_SUM_MISMATCH`、`SPLIT_SHARE_NOT_POSITIVE`、`SPLIT_WITHOUT_ME`、`SPLIT_NOT_NEEDED`（皆 400）；`SPLIT_TRANSACTION_READ_ONLY`、`SPLIT_ENTRY_READ_ONLY`、`TRANSACTION_NOT_CONVERTIBLE`（皆 409）。
沿用：`LEDGER_ARCHIVED`、`COUNTERPARTY_HAS_ENTRIES`、`LEDGER_HAS_DEBT_TRANSACTIONS`、3b-2 的提議錯誤碼。

### 5.5 寫 shared 契約時的補充（2026-10-03）

以下三點在寫 `packages/shared` 契約時補上，都只增加欄位或錯誤碼，不改既有形狀：

1. **`SPLIT_PARTICIPANTS_INVALID`（400）**：§3.4 第 1 步（名單為空、重複、我出現兩次，或分法需要的值缺了）原本沒有對應的錯誤碼。
2. **`Split.payerEntryId`**：別人先付時，付款人不一定在名單裡，那筆「我欠付款人」的往來紀錄掛不到任何一列名單上，所以單獨列出。
3. **`TransactionDebtRef.kind`**：交易型別只管資金方向，「我幫對方付」是 `LEND`（決策 89）。沒有往來種類，畫面只能寫成「借出」。

## 7. 畫面方向（已定案，細節在 `phase-3c-web.md`）

以下是三輪提案頁裡開發者已經選定的方向，畫面 spec 依此展開，不重新討論：

1. **表單順序**：金額、日期、分類、帳戶、名稱、備註，最後是分帳開關。名稱、備註都不標「選填」；既有表單的「備註（選填）」一併改成「備註」。
2. **帳戶列的切換圖示**：預設選帳戶；點圖示改成選付款人（收入叫收款人）。不連動帳本這一列預設「付款人：我」。
3. **分帳是開關**：打開後在下方列出要分的人與每人金額，預設均分。點「›」，詳細設定從右往左滑入右側欄（側欄內換頁）。子頁面左上「‹ 返回」、右上「儲存」，**不放 ✕**，避免與「右側欄 ✕ 一律直接收起」衝突。
4. **分帳選項**：均分、金額、比例三個分頁；金額與比例會自動調整（決策 94）；比例分頁顯示換算後的金額；底部有精度設定（決策 91）。
5. **用箭頭表示誰欠誰**，不用文字：`我 ──3,000──▶ 小明` 代表我欠小明 3,000，金額寫在箭頭上方。表單的預覽、列表展開的明細都用這個寫法。
6. **交易列表**：分帳合併成一列，我付時顯示總額（−$3,000）、別人付時顯示我那份，標「分帳」；點「›」在列表內展開明細，點列本身照舊打開編輯。

| 計算機鍵盤               | 參考圖的數字鍵盤                                                  | App 版再評估 |

## 10. 界線（Always / Ask first / Never）

- **Always**：份額由後端以 `computeSplitShares` 算出並存下；往來餘額與帳戶餘額一律算出；分帳的所有寫入在同一個資料庫交易裡；隔離測試先於實作。
- **Ask first**：放寬 §3.6；讓一般交易端點能改分帳的交易；把其他人的份額給擁有者以外的人。
- **Never**：在前端決定份額或零頭（只能預覽）；讓連動的對方看到分帳的總額、名單或其他人的份額；金額使用浮點數。

## 12. 核可時一併確認的兩點

以下兩點是本 spec 新提出、提案頁沒有問過的。開發者 2026-10-03 核可 spec 時照建議定案：

1. **箭頭寫法的範圍**：§7 第 5 點用在 3c 的新畫面，**既有畫面一起改**（對象清單的餘額、往來帳、總覽的待確認卡片），在 3c 畫面 spec 列出清單。理由：同一件事在 App 裡只有一種寫法，使用者才不必在兩種之間轉換。
